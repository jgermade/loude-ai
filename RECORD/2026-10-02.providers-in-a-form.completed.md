# Providers in a form

## The question

> en settings > models, en lugar de mostrar una lista con inputs, mejor se
> muestra la lista con los proveedores añadidos y que se editen en la modal

## What it was

A table of seven editable columns over a draft of the providers file, with a
*save* button under it and a change count on the button. Adding a provider was
already a form in a modal (`provider-form.html`), and it wrote that one profile
at once. The table's own edits went through the draft.

## What it is

- **The list is read-only.** One row per profile: its name, and backend, URL,
  model, window and `native tools` where set. Tags say *default*, *running*,
  *remote* and *engine*. The built-in mock is the first row, because "no
  default" in the file is it.
- **Each row has three actions.** *make default*, *use →* (a session on it)
  and *edit*.
- **The form adds and edits.** `provider-form.html` takes `editing`, the
  name, and opens on what the file has.
  - **A rename** writes the new name and takes the old one out, so it is not
    left beside it. The default follows the rename.
  - **Unticking *default*** on the current default gives it back to the mock.
  - **Kept as they were:** `remote` and `engine`, which are not fields here.
    `remote` is only ever written after the host was typed, and `engine` is
    Settings → Engines' to set.
  - **Remove** is in the form, on the left, outlined in red. The first click
    arms it (`Remove local?`, filled) and the second writes the file without
    the profile.
  - **One write.** Every save is one `PUT` of the file as the server last
    answered it with this one profile changed, so nothing else in the file
    moves.
- **The default is set from the list.** It is the one thing changed often,
  so it is written at once from *make default*. A default off this machine
  needs its host typed, the same declaration `-p` is on the command line. That
  refusal opens the profile's form with *default* ticked, where the question
  is asked.
- **What went.** The draft, `toDraft`/`fromDraft`, the change count and the
  save button.

## Rejected

- **Editing in the list and saving with a button.** The draft had to be kept
  apart from the file, and a field half-typed in one row was one save away
  from being written with an unrelated change. A profile is a few fields that
  belong together, and a form says that.
- **Remove in the list.** A destructive button on every row, one click from
  *edit*. In the form it is one profile, asked twice.

## Checked

`settings.spec.js`, extended:

- the list has no inputs and no save;
- an edit opens on the file's values and writes `model = "tiny-q4"`;
- a rename leaves only the new name;
- a remove takes two clicks and leaves the file without the profile;
- *make default* in the list moves the live session to it.

All nine pass.

Two things were found on screenshots and fixed. Remove's text was unreadable,
because it took the modal's blue background. And with Remove present, Cancel
sat centred between it and Save, because both had an auto margin.
