# The foot, the switch's feedback, and a turn you can open

Four requests from Jesús, the day after
[`a-switch-that-does-not-wait`](2026-09-29.a-switch-that-does-not-wait.completed.md):

1. put the provider and the model together under the chat, as the same dropup
   button the mode uses;
2. when the model changes, say beside that button that one model is stopping
   and another starting;
3. when an answer is waiting for a model to be ready, say so where the answer
   will go;
4. the answer's meta line should give the speed, and a click on it should open
   a modal that shows the context the turn used and the answer.

All four are built. Each section below says what it is and what it does not
do.

## One button

The picker was two pill-shaped tags (the profile and the model) and a caret
pointing right, and the mode beside it was a `Dropup` face. Two kinds of
control in one row of choices. The picker's button now copies the
`components/dropup.html` face rule for rule: one bordered button reading
`profile · model`, with the caret that opens upward. The menu stays its own,
because two columns (providers, then that provider's models) do not fit a flat
list.

It is a copy of the face and not the component. `Dropup` takes a list of
options, and its contract (`:model`, `change`) is a choice among them. Growing
it a slot for the button and another for the menu would turn it into two
components sharing one name. If a third control needs the face, the face
becomes its own component then.

The button keeps its old class (`dest`) beside the new one (`face`), because
four smoke tests click `.options .dest`. It also gives way before the
feedback does (`max-width: 60%`): the model is also on its tooltip, and the
feedback is the thing happening now.

## What the switch is doing

`Supervisor::ensure` now notes which phase it is in:

- `stopping` — the engine was running another model; `from` names it;
- `downloading` — luu's own copy, the first time;
- `starting` — loading `model`;
- then `ready` or `failed`.

The in-progress phases share **one clock**, from the first of them. A person
reads *how long since I switched*, not how long the current phase took. `ready`
and `failed` start a clock of their own. The test found that `ready` was at
first inheriting the switch's clock, against what the doc comment said. `from`
is carried from `stopping` into `starting`, so the model that was left is
still named while the new one loads.

The page shows it beside the button:

```
● stopping qwen2.5-coder:7b 0s
● starting qwen2.5-coder:14b 3s · qwen2.5-coder:7b stopped
● qwen2.5-coder:14b ready in 4s          (for three seconds)
● could not start qwen2.5-coder:14b      (the reason is the tooltip)
```

What is happening and for how long comes first. At a chat column's width, the
first version (`qwen2.5-coder:7b (ollama) → starting…`) was cut off before the
model being started, which was the one part that mattered. Names in the
feedback drop the ` (ollama)` suffix. The tooltip keeps all of it.

**The server only knows `from` when one engine restarts on another model.**
When the switch moves to *another engine*, `release_engines` stopped the old
one before the answer came back, and that engine's readiness is not the live
session's. The picker remembers the model it was on when the switch was
clicked (`ui.switchedFrom`) and names it in the same place. A switch from a
destination with no engine at all (a remote provider) shows the same line,
which is true enough: that model is no longer the one being sent to.

Polling runs every 700 ms, and only while a phase is in progress. `stopping` is
usually shorter than one poll, so it is rarely seen, and the `from` it carries
is what makes the next line say what was stopped anyway.

## Where the answer will go

A live assistant message with nothing in it yet now shows a line:

- `waiting for qwen2.5-coder:14b — loading · 3s` while the engine is in a
  loading phase (`stopping the one before it` or `downloading the engine`
  instead of `loading` when those are the phases);
- `waiting for the model…` otherwise: the prompt being processed, or a
  planning call.

It needs `ui.engine` to be current when the turn starts. A switch starts the
poll, but so can a turn on an engine nobody switched to: one that exited, or
one still starting at `serve`. So `app.html` calls `watchEngine()` whenever
`state.turn` changes. It is one request per turn, and nothing more while no
engine is loading.

## The meta line

Under each answer: how it ended, prompt and completion tokens, the speed, the
time to the first token and the total.

**The speed is over the writing, not the wait**: completion tokens divided by
the time from the first token to the end. The wait before the first token is its
own number because it holds everything that is not generation. The fake engine
below spent 3.8 s of a 4.1 s turn loading; folded in, that turn would have read
at under 2 tok/s. A turn that ran tools spent part of the writing span running
them, so its speed is a floor and says `≥`. Where the backend reported no count,
there is no speed. Zero would be a claim.

The three instants come from two clocks. A live turn uses the page's
`Date.now()` at `turn_started`, the first `token` and `ended`/`failed`. A
reloaded one uses `TurnView`'s `started_at_ms`, `ended_at_ms`, and the new
`first_token_at_ms`, which `SessionView` folds from the first `token` line's
own `at_ms`. Every number shown is a difference, so the clocks never meet.
**No protocol or record format moved**: the field is derived from lines every
recording already has, so a stream from August gets it too.

A reloaded turn also keeps its `reason` now. It was dropped, so a reloaded
answer had no meta line at all, and with the line gone went the only way into
the modal.

## The modal

`turn-inspect.html`, a `<dialog>` like every other one here (`modal.js`),
opened by a click anywhere on the meta line. A row of facts (ended, prompt,
completion, speed, first token, total) and three tabs:

- **Context**: what was asked, the budget bar and its buckets, and the prompt
  *as sent*, cut at the renderer's role markers (`<|System|>`, `<|User|>`,
  `<|Assistant|>`) so the system block and each exchange read as separate
  blocks. A prompt without markers is one block. A turn recorded without the
  trace channel says there is nothing exact to show. A tool turn says that this
  is the first call's prompt and how many tokens the round trips after it sent.
- **Answer**: the raw text, fences included. This is the one place the chat
  still shows what the model typed.
- **Tools**: each call's verdict, arguments, error and output.

Nothing is fetched. It reads the turn `state.history` already holds. The debug
inspector holds the same facts in a 20rem rail behind a turn picker. The modal
is the same facts reached from the answer somebody just read.

**Found building it: the trace can arrive after `ended`.** The trace is a
second socket. Against the mock at no delay, its `prompt` and `budget` lines
for a turn landed after the protocol's `ended`, after `keepTurn` had copied
whatever the previous turn left. The kept turn said it had been sent nothing,
and the modal said so. The trace's `prompt` and `budget` handlers now patch
the kept turn when there is one (`patchKept`). The inspector's turn picker read
the same stale copy and gets the fix too.

## Tested

- `engines::tests::the_phases_of_one_switch_share_a_clock_and_remember_what_was_stopped`:
  `stopping` → `starting` keeps both the clock and `from`; `ready` starts its
  own clock and drops `from`; another model starts another clock.
- `api::tests::a_recording_rebuilds_the_session_it_recorded` now asserts
  `first_token_at_ms` is the *first* token's stamp.
- `tests/smoke/gate.spec.js`, on the turn that runs a tool: the meta line
  reads `first token`, and opening it shows the user block `go on then`, the
  raw answer with its fence and `It is luu.`, and `read_file` under Tools, then
  closes. 23 of 23 pass against `target/debug/luu`.
- By hand, against a stand-in `llama-server` (a Python script that takes 4 s
  to "load" and then answers `/health` and a five-word stream), with a
  `[engine.fake]` on port 18091 and real `ollama:` references so `-m` resolved.
  Switching 7b → 14b read `starting qwen2.5-coder:14b 0s · qwen2.5-coder:7b
  stopped`. The server reported `from` itself, since it was one engine. A
  prompt sent at once showed `waiting for qwen2.5-coder:14b (ollama) — loading
  · 1s` in the answer's place. The answer then arrived with `first token 3.8 s ·
  4.1 s`, and the feedback read `ready in 4s`. The stand-in reports no usage in
  the shape the backend asks for, so that turn read `usage unknown` and no
  speed, which is the rule working.

**Not tested:** the `downloading` phase (it needs a managed install), and
`stopping` being seen at all. It is shorter than a poll against a process that
dies on SIGKILL, and a real llama-server unloading 20 GB may be the case where
it shows.

## Still open

- The speed of a tool turn is a floor. An exact one needs the time of each
  step's first and last token, which the stream has (`token` lines are stamped)
  and `TurnView` does not keep.
- The modal shows the first call's prompt only. The round trips' prompts are
  `ModelCall` events that never reach the wire. Showing them means a trace line
  per step, which is a format bump and the reason it was not done here.
- If a third control needs the dropup face, the face should become its own
  component.

## Appended the same day: the prompt in the legend's colours

Jesús asked whether the tools are part of the system payload. They are: the
definitions are text in the one `system` message (`Context::system_message`),
and no backend uses a native `tools` field. The budget plots them as their own
bucket only because they are counted apart. He then asked for the text to
wear the legend's colours, so that the split is visible in the prompt itself
and not only in the bar.

**The server sends counts, not spans.** The `budget` trace line says how many
tokens each bucket holds, and the `prompt` line is one string. Nothing on the
wire says where one bucket's bytes end. `ui/prompt-parts.js` reads the
boundaries back from what the renderer writes the same way every time:

- **system**: `# Tools` opens the tools block and `# Repository map` opens
  the map, each after a blank line. An authority note in `system` position
  renders last. Its words are in `/api/settings`, so it is cut off the end by
  matching them, and it stays **system**, the bucket it is counted in.
- A user message followed by an assistant message opening `[job closed]` or
  `[draft closed]` is a fold: both are **summaries**.
- Every other exchange before the last user message is **history**.
- The last user message is **code** when it opens with a fragment
  (`// path`), up to where what was asked begins, found from the end. A note
  in `prompt` position is matched by its words and moved back into **prompt**.
  Everything else in it is **prompt**.

Where a boundary is not found, the text stays in the bucket it was already in.
Nothing is guessed into another, because a colour is a claim. The cuts are
checked to rejoin into exactly what was sent. The first version doubled the
blank line between the map and a note, and that check found it.

**Rejected: spans on the wire.** A `budget` line carrying byte ranges would
be exact, but it is a record format bump. Every recording before it would draw
uncoloured, and the renderer already writes these markers deliberately.

**What it does not cover.** A planning call's instruction, rendered before the
question, is coloured as code when the message also carries fragments. Which
instruction was used is not on the page, so it cannot be matched the way a
note's words are. And an evicted or pruned turn's citation line
(`// path — N tokens, pruned`) inside a history message is coloured as
history, which is the bucket it is counted in.

**Found on the way.** The picker button collapsed to one letter at some widths.
The cause was `max-width: 60%` on a row that sizes itself to its content,
where the percentage resolved against almost nothing. It now shrinks three
times as fast as the feedback beside it, down to a floor of `6rem`.

**Tested.** `node` over the cases above (tools, map, a system note, a prompt
note, a fold, plain history, a turn with and without fragments), with each
block's pieces checked to rejoin exactly. The gate smoke test now asserts that
the system block's `.b-tools` holds `# Tools` and that the last user block's
`.b-prompt` is `go on then`. 23 of 23 pass.

## Appended the same day: the meta line, a grouped context, and the context by the composer

Three more requests from Jesús.

**The meta line is one line of flow.** It was `stop 495 prompt / 33
completion 46 tok/s first token 114 ms 827 ms inspect`. It is now
`→ 495 ← 33 - 🕑 114 ms → 827 ms - 46 tok/s`. The arrows are what went to the
model and what came back. The clock is the page's own `#i-clock` symbol rather
than an emoji, so it takes the theme's colour. How the turn ended appears only
when it did not simply stop: `stop` is every answer, and a word on every line
that is almost always the same word stops being read. The word *inspect* is
gone too. The line is still the button, and its border on hover says so.

**The context is grouped by what each piece is**, in `context-view.html`,
which the turn modal and the new context modal share. It shows one card per
bucket in the legend's order: system, tools, map, summaries, history, code,
prompt. Each card has its count and its colour. An exchange under history or
summaries keeps its speaker. `prompt-parts.js` gained `group`, which gathers
`paint`'s pieces by bucket (two pieces of one message in one bucket read as
one), and `split`, moved out of the turn modal so both modals cut the prompt
the same way. **No block scrolls unless asked to.** A card over 24 lines or
2 400 characters is clipped to about seventeen lines with a fade, and offers
*show all* (the whole of it, inline) and *scroll* (a box of its own). Every
block used to be a scroll box capped at 28rem, which put a scroll bar inside
a scrolling modal for the three-line system prompt. Each card carries its
bucket as `data-bucket`, which is what the tests address it by.

**The composer: the clip on the left, the context on the right.** The clip,
which names the open file in the prompt, moved to the left of the input. Its
old place, the right end of the options row, is now the context indicator: the
newest turn's buckets as a 56px bar in the legend's colours, filled against
the window where the window is known, and the tokens sent (`1.5k / 8k`, or
`1.5k` where the window is unknown). It is disabled until a turn has been
sent, because the context is measured when a turn is built. A click opens
`context-modal.html`, the grouped view of the newest turn under a row of
facts: tokens sent, the window, the share used (amber from 80%), the reserve
kept for the answer, and what the server counted. That last one differs from
ours by the chat template and, under native tool calls, by the tools the
server rendered.

**Tested** in the gate smoke test: the meta line has its arrows, the turn
modal's `tools` card holds `# Tools` and its `prompt` card is `go on then`,
and the indicator opens the context modal on the same `prompt` card. 23 of 23
pass. By hand in a browser: the *scroll* toggle turns a clipped card into a
scrolling box and back.

**And the share of the window**, asked for next: the indicator reads
`482 / 8.2k 6%` (amber from 80%, red from 95%), the turn modal's facts gain
*context 6%* for their own turn, and the context view's sent line ends
`…of a 8192-token window, 6%`. Where the window is unknown, which is Jesús's
`llama_cpp` profile as it stands, with no `context-limit` against a server
serving 32 768, all three say `—` and why, rather than a percentage of
nothing. Checked in a browser once with `--context-limit 8192` and once
without.

**And the picker's menu has a fixed height** (`min(60vh, 26rem)`), where it
used to fit the focused provider's list between 10rem and 26rem. It opens
upward from its button, so a height that followed the list moved the menu's
top edge every time the pointer crossed a provider with more or fewer models.
Each column now scrolls inside it. Measured hovering between two providers:
the top edge stayed at 463px and the height at 450px.

**Then partial over total, not a percentage**, asked for straight after: the
indicator reads `482 / 8.2k`, the turn modal *context 482 / 8192*, the
context view `482 / 8192 tokens`. Where the window is unknown each reads
`… / —` and says why. The share is still computed, to turn the count amber
from 80% and red from 95%. The meta line puts the speed first:
`155 tok/s - → 0 ← 34 - 5 ms → 225 ms`. Its symbols take their colours only
on hover, and the hover is also the hint that the line opens.

**Found: the indicator came back disabled after a reload.** It, its modal and
the inspector's live panel read `state.budget`, `state.prompt`,
`state.prefix` and `state.extraCalls`, and only trace lines arriving live ever
filled those. A page reloaded, or a session resumed, had its turns back in
`state.history` and nothing in the four. `refreshLiveSession` now sets them
from the newest stored turn, with `backendPrompt` from its usage. The gate
smoke test now reloads and opens the context modal again.

**Seen and not explained: a reactive loop.** Twice in a row, the full smoke
run logged `jq79: an effect re-woke itself 100 times in a row (it writes what
it reads)` during the gate test, and failed it for logging an error. That test
passed alone, and the full run passed in the next seven runs, three of them
with jq79 patched to print the effect's source, then restored. No effect in
`app.html` or the components written today reads what it writes except
`maybeAnswer`, which settles in two passes. A page that loops like this
spends a frame's worth of work a hundred times and then gives up, and a page
that had frozen would be consistent with it, so it stays open here with the
instrument that would name it: print `String(c)` at that `console.error` in
`vendor/jq79.js`.

**The reactive loop, found.** It came back during the next change, three
failing runs in a row. With jq79 patched to print the looping effect, all
three named the same one: `$: budget = state.budget` in `context-modal.html`.
Assigning an object that belongs to one reactive store (`state`) to a field of
another (the component's own) makes jq79 wake the effect that reads it on
every pass, a hundred times, and then give up with an error. That explains
why it was intermittent: it fires only while the context modal is open and
`state.budget` changes under it, which the gate test's reload now does. The
modal reads `state.budget` where it uses it and copies it nowhere. Three runs
after the fix: 23 of 23 each. The one other statement of that shape,
`$: proposed = state.pending` in `app.html`, predates today and never appeared
in the instrument. It is left alone and named here.
