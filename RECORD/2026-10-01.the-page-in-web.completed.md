# The page in `web/`

## The move

`crates/luu/ui/` is now `web/`, at the root of the repository.

The page was a folder inside the crate that serves it, because until now one
binary served one page to one machine. The direction discussed on this day
changes that premise: a `luu` on a VPS, perhaps serving the page for sessions
that live on other machines, perhaps as a PWA. Nothing in that direction is
decided yet. It needs its own record, and it has to argue with
[`2026-09-04.sessions-stay-home`](2026-09-04.sessions-stay-home.completed.md)
and [`2026-09-16.what-the-debug-ui-does-not-need`](2026-09-16.what-the-debug-ui-does-not-need.completed.md).
What *is* decided is that the page is a surface of its own, and a path that
says it belongs to one crate says the opposite.

Nothing about how it is built changes. `rust-embed` reads `../../web/` from
the crate: from disk in debug builds, baked in for release. `cargo build`
still needs no node. Monaco is still an optional node dependency, now in
`web/node_modules`. The crate is not published to crates.io, which is the one
place a folder outside the crate would stop being packaged. The Containerfile
copies the whole tree.

## What it touched

`serve.rs` (the embed folder, Monaco's root, their comments), `ui_versions.rs`
(`include_str!` of `store.js`), the Makefile's `WEBUI`, CI's site assembly,
the two smoke configs' comments, `AGENTS.md`, `luu-design.md`, and four files
in the page that name their own folder, one of them in text a person reads
(the Monaco caveat in Settings → General).

**Links from `RECORD/` into the old folder now dangle**: 10 of them, in 6
records. They are left as they are. Records are append-only, and there is
precedent: the rename of `loude-design.md` left its links in the records that
cite it. A link in a record says what it pointed at on the day it was
written, and `git log --follow` finds the file.

## Found on the way: the static twin was failing

The static twin's own suite (`site.spec.js`, the `web` job in CI) failed all
five of its tests, and for reasons unrelated to the move: the page asked a
server that the static host does not have. During a replay it requested
`/api/engine` and `/api/settings`, the static host answered 404, and the suite
fails on any console error. With the page as it was before this day, one
replay of `eviction-turn.jsonl` made **312** requests to `/api/engine`, one
per token, the same bug
[`2026-10-01.a-slow-disk-is-one-slow-request`](2026-10-01.a-slow-disk-is-one-slow-request.completed.md)
fixed on the live page. It began with the engine poll in `510ee3d`.

Two guards, next to the one `hello` already had:

- `watchTurnEngine` does nothing in a replay: a recorded turn waited on no
  engine this page can ask about.
- The settings refresh at the end of a turn is skipped in a replay, like the
  one after `hello`.

After them, the same replay makes no requests that fail, and the five tests
pass.

## Also found: fixtures recorded against the wrong backend

`make-fixtures.sh` used the state directory of whoever ran it. On a machine
whose `config.toml` has a default profile, `luu chat` sent to that profile
instead of the mock. On this one that is a local engine: the script started a
real llama-server and hung. CI has no config, so it never saw this. The script
now makes its own `LUU_HOME` in a temporary directory and removes it on exit.
On this machine, with the real config present, it records all 11 fixtures in
32 s and starts no engine.

## Appended the same day: Settings → General drew nothing

Reported as "the General view of Settings does not load". The section's setup
script awaited `GET /api/icon-theme` before anything rendered, and that request
sometimes takes tens of seconds. It is the same slow read as the freezes in
[`2026-10-01.a-slow-disk-is-one-slow-request`](2026-10-01.a-slow-disk-is-one-slow-request.completed.md).
After that fix the server keeps turning, but the request itself still waits,
and General waited on it: theme, editor, layout and folder, all behind a
question only the icon rows ask. jq79 said so in the console after 3 s.

Seen here: one hang on a fresh server at 06:27Z, given up at 10 s, and two
more in a browser in the same minutes. Then nothing in 25 fresh servers in a
row. With copies of the binary re-signed so endpoint security had not seen
them, 2 of 9 hung for **over 60 s** and **43.8 s**, and the other 7 answered
in about 45 ms. This machine runs CrowdStrike Falcon and Microsoft Defender as
Endpoint Security extensions, both of which can hold a file open while they
decide. That makes them the suspect. **It is not shown.** Six freshly compiled
C programs read the same 78 `package.json` files in 15–48 ms, so a binary
being new is not enough to cause it. No `sample` caught a hang: each time one
was ready, the hang did not come.

The fix is on the page, and it does not depend on the cause: General asks for
the icon theme without awaiting it, as it already did for Monaco. The icon
rows say *asking the server…* until the answer comes. With the answer held 8 s
on the network, the section draws in 2 ms and the theme fills in at 7.9 s. The
live smoke suite passes, 23 of 23.

Still open: the cause. The way to find it is a sample taken *during* a hang,
which needs someone to be there when it happens. The watchdog could do that:
it already knows when a request has been in flight for five seconds.
