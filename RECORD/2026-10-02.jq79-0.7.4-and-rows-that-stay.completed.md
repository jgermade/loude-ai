# jq79 0.7.4, and rows that stay

## The question

Jesús, on a long snippet arriving in the chat:

> cuando el agente está devolviendo un snippet largo, el texto baila mucho, y
> parece como que se está redibujando muchas veces

and, a few messages later, on the tree:

> al abrir una carpeta en el arbol de ficheros el scroll vuelve al principio en
> lugar de no hacer nada

Both were the same thing.

## What it was

jq79 0.7.2's keyed `:each` kept a row only when the item under its key was
**the same object** as last time (`Object.is(f.item, P)`). A new object under
the same key was disposed and rendered from nothing, with its DOM, focus and
scroll. And it never woke a row for a property assigned inside an item. That
second fact is in
[`walking-skeleton`](2026-08-26.walking-skeleton.completed.md), and it is why
`store.js` replaces messages rather than mutating them. The comment there says
"`:key` keeps the DOM", which was not true: replacing the item rebuilt the row.

The page recomputes its lists from fresh objects:

- `entries` in the chat, on every token;
- `rows` in the tree, on every folder opened.

So every row was rebuilt every time. Measured with a probe that counts, frame by
frame, how often each element is a new node while a 60-line snippet streams in:

| | rebuilt in frames (of 121) |
| --- | --- |
| the user's message, which does not change | 117 |
| the reply, its `<figure>`, its `<code>` | 117 |

In the tree, rebuilding every `<li>` emptied the list for a moment, and that
threw the scroll back to the top.

## What it is

### `helpers/rows.js`

`keeper()` hands back last time's object for a key whose fields are all the
same as last time (one level deep), and a new object only where something
changed. The chat's `withParts` uses it, for rows and for parts. So does the
tree's `flatten`. Two attempts that did not work came first, and are kept here
because they are the obvious ones:

- **One `$reactive` object per row, mutated in place.** jq79 tracks by path
  inside its own store, and an independent `$reactive` inside the array is a
  different store. The row's bindings never heard the writes. Deferring the
  writes to a microtask changed nothing.
- **One plain object per row, mutated in place, with `entries` reassigned.** The
  `:each` kept the rows, since they were the same objects, and their bindings did
  not re-run.

With the keeper and 0.7.2, rows that did not change stayed (the user's message:
117 → 0). The row being written was still rebuilt on every token. That was the
limit of what luu could do without changing jq79, and Jesús, who maintains it,
asked for the bug.

### jq79 0.7.4

0.7.4 keeps a keyed row that is handed a new object. It writes the new item into
the row's scope and re-runs the row's bindings, instead of disposing it. The
same probe, with 0.7.4 and the keeper:

| | rebuilt in frames (of 121) |
| --- | --- |
| the user's message | 0 |
| the reply, its `<figure>`, its `<code>` | 0 |

The code grew by 1129 characters over those frames, in place, and was coloured
when the highlighter answered.

- **Vendored with its source map.** `web/vendor/jq79.js.map` is the
  published one, with every source inlined.
- **luu's one patch is applied again.** `importResource` in 0.7.4 still
  hands a bare `.html` specifier to `fetch()`, which never reads the import
  map. The patch inserts 71 characters at column 1939 of line 18. The map's 45
  segments after that column on that line were shifted by 71. Two probes after
  the edit (`Wo=` and `Kt=`) land on the right lines of `jq79.ts`. This is still
  for upstream.

### A regression in the viewer, worked around

Under 0.7.4 the open file stopped following the disk: `workspace.spec.js`
"follow the disk" failed every time, and passed every time with 0.7.2. The
chain `$: shown = workspace.content` → `$: rows = filing ? fill(shown) : ""`
did not re-run when a re-read replaced `workspace.content` with an object of
the same keys. `fill` reads `content.path`, which does not change, inside the
effect, and `content.lines` only in a `requestAnimationFrame`, outside it.

- **The workaround** is to read what changes where the statement is:
  `fill(shown, shown.lines)`.
- **Not isolated.** Three minimal repros outside luu did not reproduce it:
  the same chain, the same shapes, a field read late. The reliable repro is
  that test with the debug binary and the line put back.

### `$destroyed`, `$attached`, `$detached`

0.7.4 has an unmount hook. These had worked around its absence, and now use
`$destroyed`:

- `modal.html`: it disconnected its `fit` on the first measurement after the
  dialog left the document, and the ESC listener removed itself the same way.
  It now also gives the parent back its `inert` when a child is unmounted
  without a close, which before would have left the parent inert.
- `scrollable.html`, `segmented.html`, `rail.html`: observers never
  disconnected.
- `engines.html`: a poll that stopped when its pane was not in the document.
- `dropup.html`: a `keydown` on `window` per mount, never removed. Every dropup
  ever drawn kept one.

## Checked

- **Suites:** the live suite and the static twin pass. `workspace.spec.js`
  "follow the disk" fails with 0.7.4 and the line put back, and passes with
  the workaround.
- **The chat:** the counts above, from the probe.
- **The tree:** a new test opens folders with `click()` from the page, not
  Playwright's, which scrolls the row into view first. It asserts that the
  row at the top of the view does not move and that the first `<li>` is the
  same node.
  - Without the keeper, it **fails on 0.7.2** and passes on 0.7.4, so 0.7.4
    alone fixes the scroll.
  - `scrollTop` may still grow when rows open above the view. That is the
    browser's scroll anchoring keeping the view still, and the test allows it.

## Still open

- The viewer's regression has no isolated cause. It is a question for jq79,
  with the repro above.
- The bare `.html` specifier patch is still luu's.
- No test checks that the `$destroyed` teardowns run, only that nothing broke.
