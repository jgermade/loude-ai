# One modal

## The question

Jesús, on how the modals were written:

```
asModal("settings-dialog", { close: closeSettings })

<dialog id="settings-dialog">
```

Two objections. He would rather the page used no HTML ids, and a modal
should be one generic component rather than seven copies of a pattern.
And while at it, `@web` should name the `web/` folder, so an import
stops climbing with `../`.

## What it was

Seven `<dialog>`s (settings, folder picker, session starter, turn, context,
provider form, engine form). Each one wrote the same head, the same close
button and the same `@click.self`. Each one called `asModal(id, …)` from its
`:setup`, and its store's close function called `closing(id, done)`. The id
was the only thing both sides could name, so `lib/store.js`, `lib/ui.js` and
`lib/workspace.js` each reached into the DOM by a string to play an
animation. `asModal` also polled for up to 120 frames for the element to
exist, because it ran before the template it was looking for had rendered
(see [`2026-09-18.the-window-rules-are-a-session-fact`](2026-09-18.the-window-rules-are-a-session-fact.completed.md)
part 4).

## What it is

`web/components/modal.html`, one component, flat beside the others:

```html
<Modal title="Add a provider" width="34rem" :open="open" @close="close?.()">
  <template :slot.head><span class="dim">beside the title</span></template>
  <section class="modal-body">…</section>
</Modal>
```

- **The `<dialog>` is the component's**, so it is found with `$self("dialog")`
  and has no id. The waiting is the component's too: it waits for its *own*
  template with `await $mounted()`, and then for that template to be in the
  document, because mounted inside an owner is not the same as connected,
  and `showModal()` throws on a dialog that is not.
- **Content arrives by slots.** The default slot is the body, and `head` sits
  between the title and the close button (the turn's model, the context's
  "as of turn"). Slot content is the owner's, scope and scoped styles
  included, so `.facts` in `turn-inspect.html` still reaches it. The other
  way round does not hold: an owner's scoped `.modal.wide { width }` never
  reached the component's dialog. That is why width is a prop now.
- **Every way out is one exit.** The close button, the backdrop, ESC and
  `:open` going false all play the 140 ms exit and then emit `close`. The
  owner clears its flag in answer. `:open` is for a script: the two forms set
  it false once a save lands, and they leave the way a click on close does.
  `locked` refuses all of them and hides the close button.
- **The store's close functions only clear state.** `closeSettings` is
  `state.settingsOpen = false`. Nothing in `lib/` names a modal any more, and
  `lib/modal.js` is gone. The ESC ladder in `app.html` asks
  `document.querySelector("dialog[open]")` directly.
- **The box's styles moved into the component**: the dialog, its backdrop,
  the keyframes and the head. `.modal-body`, `.modal-foot` and
  `.modal-actions` stay in `app.css`, because what goes inside a modal
  belongs to its owner.

One trap, found while writing it: `$emit` dispatches a *bubbling*
`CustomEvent`, and the component emits `close`, which is also the name of
the dialog's native event. A provider form inside Settings would emit a
`close` that bubbled through Settings' `<dialog>` and closed that too. Both
native listeners check `event.target === dialog`.

`views/settings/engines/engines.html` polled while `#engines-pane` existed,
and cited `modal.js` as its precedent. It now asks whether
`$self(".engines-pane")` is still connected. The ids left in `web/` are
the SVG `<symbol>`s and a `<datalist>`, which `href` and `list` can only
reach by id, and three in `views/editor/editor.html` (`monaco-host`,
`code-rows`, `code-pending`). Those three were not part of this change.

## `@web/`

An import map in `index.html`, `{ "@web/": "./" }`, before the first module
script. Every import that left its own folder now starts with `@web/`.
Imports that stay beside the file (`./context-view.html`,
`./general/general.html`, `./store.js`) are still relative.

That works for `.js` and, in jq79 0.7.2, not for `.html`. jq79 passes a bare
specifier through on purpose ("they belong to the import map or the
bundler"). That is right for `import()`, which reads the map, and wrong for
the `fetch()` that loads a component, which never reads one: `fetch("@web/…")`
asks for a path under the page. The vendored file now changes one
expression: a bare `.html` specifier goes through `import.meta.resolve`
before `fetch`, and falls back to the old behaviour if nothing maps it. It
is luu's patch on jq79's file. It should go upstream into
`importResource`, and the vendored copy can be replaced when it lands.

## Checked

- The live smoke suite passed 23 of 23 against the debug binary, which
  serves `web/` from disk. The first run failed 3. All three were the
  starter's selector, `.modal.narrow`, a class that no longer exists. The
  tests now find dialogs by role and accessible name
  (`getByRole("dialog", { name: "Add a provider" })`). The component sets
  `aria-label` from its title, which nothing had done before.
- The static twin passed 5 of 5. It is served by `python3 -m http.server`,
  so the import map is resolved by a plain host, not by luu.
- A browser probe on a live server, with the console recorded:
  - ESC on the forced folder picker leaves it open, and it has no close
    button.
  - ESC on the provider form over Settings closes the form and leaves
    Settings open.
  - A click on the backdrop closes Settings.
  - No errors and no warnings.
