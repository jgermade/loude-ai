# Native tool calls: the model's own tool prompt, and our loop unchanged

## The problem

Jesús asked a 7B to "check files in project" and then to "go ahead and read
it". Four turns, `tools 0` in every one. The model answered in prose and, on
the third turn, invented the contents of `src/main.rs`, the path in our own
preamble's example. Nothing denied a call: the draft's floor grants read on
`.` and `read_file` was offered. The model never tried.

[`the-tool-call-probe-run`](2026-09-14.the-tool-call-probe-run.completed.md)
had already measured this: **3 of 15** clean calls from `qwen2.5-coder:7b` on
prompts that each name a file, under the fenced format. The design has said
since the first tool record what the next step is: *"Native function calling —
JSON Schema definitions and a `tool_call` from the backend — replaces that
function and nothing above it. Not built."*

## What the server does with `tools`, measured before building

Against Jesús's running `llama-server` b11236 (luu's managed copy), serving
`qwen2.5-coder:7b` out of Ollama's store, one request with a `tools` field and
nothing else changed:

- `/props` reports `supports_tools: true` and `supports_tool_calls: true`. Jinja
  is on, and the template is Qwen's own. With `tools` present it renders
  **the tool prompt the model was trained on**: `# Tools … <tools>{json per
  tool}</tools> … return a json object …` inside the system turn.
- The model then calls, on prompts much vaguer than the probe's:

  | prompt | reply |
  | --- | --- |
  | read AGENTS.md and tell me what it is | `read_file AGENTS.md` |
  | can U check files in project? | a sentence, then `list_dir` |
  | go ahead and read the readme | `read_file README.md` |
  | what does Cargo.toml say about the workspace? | a sentence, then `read_file Cargo.toml` |
  | list what is in the crates directory | `list_dir crates` |
  | hi | "Hello! How can I assist you today?" |

- **But never as `tool_calls`.** Every call came back as `content`, inside a
  ```` ```json ```` fence: `{"name": "read_file", "arguments": {"path":
  "README.md"}}`. The template asks for `<tool_call>` tags, which the server's
  parser looks for, and this model writes a JSON fence instead. It is a known
  habit of Qwen2.5-Coder.

So the gain is **the prompt**, not the parser. A server that parses the call
is a bonus we have to accept when it happens, and cannot count on.

## The proposal

**A destination chooses its transport**: `tool-calls = "native"` on a
profile, or `--tool-calls native` for one run. The default stays `fenced`, and
the reason is not caution: every recording in `RECORD/runs/` was made under
it, and a default that moves makes every earlier run a different arm without
saying so. The header records the choice (`tool_calls`, `record::FORMAT` 19;
absent means fenced, which is what every earlier stream was).

**Under `native`, everything above the backend stays as it is.**

- **Out:** `CompletionRequest` carries `tools: Vec<ToolSpec>` (name,
  description, parameters). Empty is fenced. The backend sends them in the
  API's `tools` field, and the system message leaves out our fenced preamble
  and schemas (`Context` renders it without them, and the `tools` bucket counts
  the specs' JSON, which is what is actually sent). The history is still
  rendered as it always was, `assistant(text with the call) · user([name]
  result)`. **The backend converts it**: an assistant message with a call,
  followed by the user message that is that call's result (it opens with
  `[name]`), becomes an assistant message with `tool_calls` plus a `tool`
  message. The pair is found, not guessed. The design already guarantees it:
  a turn is evicted whole, so a result never loses its call.
- **In:** a call the server did parse (`delta.tool_calls` on the OpenAI API,
  `message.tool_calls` on Ollama's) is handed up as the canonical fenced text,
  ```` ```tool\n{"name": …, "arguments": …}\n``` ````, after the prose that
  came with it. A call the server did *not* parse is already text.
  `parse_call` learns the ```` ```json ```` fence beside ```` ```tool ````. It
  already found the bare object, but the page and the history also need the
  block recognised as one unit.

This is what "replaces that function and nothing above it" costs in practice:
one transport module, the parser learning one fence, and the context leaving
out one block. The loop, the steps, eviction, folds, the stored text, the
protocol and the page's cards stay as they are.

**What it costs.**

- The stored text of a turn whose call the server parsed holds our canonical
  fence rather than the model's bytes. The model's bytes were never shown to
  us, and the server's parse is the only form of them we have. Said here so
  a reader of a recording does not take the fence for something the model
  typed.
- `prompt_sent` in the trace is our rendering of the messages. Under `native`
  the server renders the tools and its own tool prompt around them, so
  `usage.prompt_tokens` against our count now includes that tool prompt as
  template overhead. The panel already reports that gap, and this makes it
  bigger.
- A server that cannot take `tools` refuses the request loudly (a 400 from
  llama-server without Jinja, Ollama's "does not support tools"), and the turn
  fails and says so. That is not a fallback, per
  [`local-first`](2026-09-01.local-first.completed.md)'s rule. The fix is the
  profile's one line.

**Rejected.**

- *Native as the default.* See above: the default is what every earlier run
  was measured under. Jesús's profile gets the line, and a run says which arm
  it was.
- *Carrying `tool_calls` through `Message`, the context, the store and the
  protocol.* Exact, and it would touch every layer the design says a transport
  must not touch, for a structure that one backend function can rebuild from
  an invariant the design already holds.
- *A second, "native" preamble of our own.* The point is the template's prompt,
  which the model was trained on. Writing our own imitation of it is how the
  fenced format got to 3 of 15.

## What decides it

The probe's fifteen prompts, one `luu chat` each, against the same
`llama-server`, `--temperature 0 --seed 7`, **one flag apart**: `--tool-calls
fenced` against `--tool-calls native`. The count is turns in which a call was
made (a `tool_call` in the recording) and which calls ran. The Ollama number
from 2026-09-14 is from another server and is not the baseline. The fenced arm
here is.

## Built, and the run

Built as proposed. `CompletionRequest::tools`, `backend::native` (the history
conversion out, the canonical fence in), both backends, `parse_call` and the
page learning ```` ```json ````, `Context::with_native_tools`, the profile key
`tool-calls`, the flag `--tool-calls`, the header's `tool_calls`
(`record::FORMAT` 19) and a *Tool calls* column in Settings → Models. The Models
table writes nothing for `fenced`, so a file that never said is left
byte-for-byte as it was.

**The run.** The probe's fifteen prompts, one `luu chat` each, against
Jesús's `llama-server` b11236 serving `qwen2.5-coder:7b`, `--temperature 0
--seed 7 --context-limit 8192`, one flag apart. It used a policy that reads the
tree and runs nothing, with `--max-tool-steps 1`, so the only question was
whether the first reply called:

| arm | a call made | a read or a list, allowed |
| --- | ---: | ---: |
| `fenced` | **7 / 15** | 5 |
| `native` | **15 / 15** | 12 |

The three native calls not allowed are the three `run_command` prompts, denied
by the probe's policy, which is what the policy was for. They count as calls
made because that is the question.

The eight fenced misses were not refusals. Two were the edition question and
the second heading answered from nothing ("edition 2018"). Three were
directory trees the model made up. Three were call-shaped text in no form
anything reads (a ```` ```json ```` object with no name, a fence tagged with
the tool's name, a bare listing). Under native, the same prompts named the
right tool with the right argument every time. The fenced arm on this server
scores better than 2026-09-14's 3/15 over Ollama. That is another server with
another template, and the reason the baseline here is this server's own
fenced arm, one flag apart.

**The round trip.** One full turn under native, no step limit: `read AGENTS.md
and say what its second heading is`. The model called `read_file`. The result
went back as a `tool` message, and the server took the converted history
without complaint. The answer was right ("Where things live").

**And it called a tool nobody asked for.** Between the read and the answer,
the model called `edit_file` on `AGENTS.md` and inserted a duplicate of one of
its own paragraphs. The run was `luu chat`, whose sandbox is the policy file
as written, and `luu.toml` grants `.` read-write, so the edit went through. It
was reverted with `git checkout` straight after; the file had nothing else
uncommitted. This is the finding, not an incident to forget. **A model that
calls tools also calls tools nobody asked for.** Under the fenced transport the
7B rarely called anything, and that hid it. In `serve` a draft runs under the
floor, where every grant is read-only
([`the-drafts-floor`](2026-09-21.the-drafts-floor.completed.md)), and that
edit would have been denied. `luu chat` and `luu stdio` have no floor. A
one-shot is approved by whoever typed it, and it gets whatever the policy file
grants. That was true before today, and today is the first day it was
exercised.

**Where the default stays.** `fenced`, for the reason above. The line that
moves a profile is `tool-calls = "native"`, or the column in Settings.

## Still open

- **`luu chat` against a write-granting policy.** Whether a one-shot should run
  under the floor unless its script opens a job, as `serve`'s drafts do. It is
  a change to what `chat` has always been, so it belongs in its own record, and
  this one is its evidence.
- **The 14B and Ollama's own `/api/chat`.** Both arms of both, one flag apart.
  Ollama parses calls with its own template, so there `tool_calls` may
  actually arrive as `tool_calls`, which is the half of `backend::native`
  this run never exercised against a real server. The wire test covers its
  shape.
- **A model that writes the template's tags.** `llama-server` parses
  `<tool_call>` into `delta.tool_calls`. That path is tested against a stub,
  never against a model that writes them.
- **The template's tool prompt is not in `prompt_sent`**, so the turn modal
  shows the tools bucket's count and says where the text went, not the text.
  `/apply-template` on llama-server would return the exact prompt. That is a
  request per turn, and a question for the debug panel rather than for the
  transport.
