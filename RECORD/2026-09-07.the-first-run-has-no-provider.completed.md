# The first run has no provider: an empty state, the models behind it, and the session that picks one

**Status:** a proposal, and the code it plans.

[`configuring-from-the-browser`](2026-09-07.configuring-from-the-browser.completed.md)
put the providers file behind a form and closed with the honest limit:

> **Nothing in the modal changes the running server.** `serve` resolved its
> destination at startup and keeps it. […] Choosing a provider for the *next
> session* is the natural next item and is ordered, not built here.

That limit is survivable on a machine that is already configured, and it is not
survivable on one that is not. This record is about the run where the file does
not exist yet, and about the two things a person needs before they can write it:
**which models the destination actually serves**, and **a session that starts on
what they just chose**.

## The problem

Three facts, in the order somebody meets them.

**1. A fresh machine reaches nothing, and the page never says so.** With no
`config.toml` and no flags, `provider::resolve` falls to `BackendKind::Mock`
([`provider.rs`](../crates/luu/src/provider.rs)) — a destination that is nowhere.
`Resolved::line()` returns `None` for it *on purpose*, so even the terminal is
quiet. The browser then opens on a chat box that answers, in sentences, from a
fixture. Nothing on the page distinguishes that from a model. The one surface
built for a person who did not start the process is the one surface that does not
say the process has nowhere to send.

**2. The model field is a text input, and a wrong model is a 404 four turns
later.** `[provider.<name>].model` is typed from memory. Ollama knows what it has
pulled (`GET /api/tags`) and every OpenAI-compatible server answers
`GET /v1/models`; nothing in this repository has ever asked either. A form that
can ask and does not is how `qwen2.5-coder:7b` gets written on a machine that
pulled `qwen2.5-coder:7b-instruct`.

**3. One process, one destination — decided before the page existed.** `App`
holds one `Arc<dyn Backend>`, one `model`, one `Budget` and one `counter`, all
resolved in `bind`. So the *end* of a first run configured from the browser is
"now restart `luu serve` from the terminal you were trying not to need".

## The proposal

Three pieces, in that order, each usable without the next.

### A. The server says it has nowhere to send, and the page opens there

The rule is the server's and is computed once, where the resolution happens.
`resolve` gains the field `window_from` already demonstrates the shape of:

```rust
pub enum DestinationFrom { Flag, Profile, Default }
```

`Flag` is `--backend`/`--ollama-url`/`--openai-url` — somebody typed a
destination, and `--backend mock` is a destination somebody chose. `Profile` is
the file answering, including a profile that names no backend. `Default` is the
mock nobody asked for: no file, or a file with no `default` and no `-p`.

`GET /api/settings` carries `unconfigured: destination_from == Default`, and the
page **never re-derives it** — the same inversion the last record landed for
`is_this_machine`: one implementation of a rule, on the side that owns it.

When it is set, the browser opens the providers editor on load instead of
waiting to be clicked, with the first-run sentence above the table, and the
composer says where a prompt would go (the mock, which is nowhere) rather than
pretending. The modal still closes: an empty state that cannot be dismissed is a
wall, and somebody wanting to read a resumed session should not have to
configure a provider first.

### B. A provider lists its models

`Backend` gains one method beside `stream`:

```rust
fn models(&self) -> BoxFuture<'_, Result<Vec<String>, BackendError>>;
```

with a default returning empty — *this destination does not offer a list*, which
is a fact and not an error. Ollama reads `GET /api/tags`, the OpenAI backend
`GET /models` with the key it already holds, the mock answers `["mock"]`.

`GET /api/providers/{name}/models` resolves that one profile out of the file,
builds a backend for it and asks. It reaches the network on a request, so it is
bounded by a short timeout and its failure is a **200 with an empty list and the
reason** rather than a 502: a provider that is not running right now is the
normal case on a laptop, and it must not read as a broken page. The model field
stays typable — a `datalist`, not a `select`, because a model that is not pulled
yet is a legitimate thing to write down.

**This is the first request that leaves the machine because a browser asked it
to**, and that is worth stating plainly. It leaves for a destination already
written in the file, it carries no prompt and no repository content, and for a
remote profile the host was typed by a person to get into that file at all.

### C. A session starts on a chosen provider and model

`POST /api/sessions` takes an optional `{ provider, model }`. The destination
becomes the **live session's**, not the process's: `backend`, `model`, `budget`
and `counter` move into one `Destination` struct behind an `RwLock`, swapped in
`create_session` before the new stream's header is written — so the header says
what the session ran on, which is the whole reason it exists. Nothing switches
inside a session, and the mid-session switch stays rejected exactly where
[`configuring-from-the-browser`](2026-09-07.configuring-from-the-browser.completed.md)
left it.

The model offered defaults to **the last one used with that profile**, read from
the store: the `sessions` table already keeps `backend` and `model`, and gains a
`provider` column (schema 3, migration adds the column and touches no row) so
two profiles on one host are not one memory. Order of the default: last used with
this profile → the profile's own `model` → the first model the provider listed.

**Off loopback, the switch is allowed only to a profile that stays on this
machine.** The write route is loopback-only because a `default` outlives the
session and the gate; a session's destination dies with the session, so the same
argument does not reach it — but *this machine's prompts leaving it, to a
destination picked by whoever holds the bearer token*, is the harm underneath
that rule, and it is the one case worth keeping. `is_this_machine` decides it,
server-side, in the one place it is already implemented.

## What it costs

- **A `RwLock` in front of four fields that were immutable**, read on every turn.
  Cheap, and the discipline is not: a reader that holds the guard across an
  `await` is a deadlock the tests will not reliably find. Every call site takes
  an `Arc<Destination>` clone and drops the guard.
- **A record file spanning a switch misstates its header.** `--record` writes one
  header at file creation, and a second session in the same file was already
  described by the first one's. A changed *destination* makes that wrong rather
  than merely coarse. Not fixed here; named below.
- **The page now reaches a provider on the browser's behalf.** Bounded and
  content-free, and still a request the machine did not make on its own.
- **The store gains a column for a UI memory.** Defensible only because the row
  it hangs on is already there; a second state file would have been worse.

## What was rejected

| | why |
| --- | --- |
| Writing the chosen model back into `config.toml` on every session start | The file is what a person wrote; a session start is not an edit. It also loses comments (already a known cost) on an action nobody asked to be a save |
| A separate `recent.toml` for the last-used memory | A second store of machine state, to keep in sync with the first one, for one string per profile |
| Deriving "unconfigured" in the browser (`backend === "mock"`) | It is the same class of mistake as reimplementing `is_this_machine` in JavaScript, and it would call a deliberate `--backend mock` run unconfigured |
| A modal that cannot be closed until a provider exists | A wall in front of a page that also reads history, which needs no provider |
| A `<select>` of models, closed | A model that is not pulled yet is a legitimate thing to type, and a list that fails closed would forbid it |
| Switching provider mid-session | Unchanged from the previous record: every per-turn number is backend-specific, and one label over two backends is a comparison nobody can make |

## Still open

- **The record file's header after a switch.** A second `Header` line mid-file is
  a format change every reader would have to accept; refusing the switch while
  `--record` is on is arbitrary. Left as it was, and now visible.
- **Nothing tests `PUT`/`POST` over HTTP against a real file**, for the reason
  the last record gave: `Config` reads the environment rather than taking its
  path. This record adds two more routes with the same gap.
- **A model list is a snapshot.** Pulled between one open and the next, it is
  stale, and the page reads it once per open like everything else in the modal.

## 2026-09-07 — what building it decided

Code, in the shape argued above. `DestinationFrom` in
[`provider.rs`](../crates/luu/src/provider.rs), `Backend::models` in
[`backend/mod.rs`](../crates/agent-core/src/backend/mod.rs) with Ollama, OpenAI
and mock implementations, `Destination` and `GET /api/providers/{name}/models`
in [`serve.rs`](../crates/luu/src/serve.rs), a `provider` column in
[`store.rs`](../crates/luu/src/store.rs), and the first-run banner and the
session starter in [`app.html`](../crates/luu/ui/app.html). Six things the plan
did not know.

**The `RwLock` was the easy half; the counter was the one that had to be
plumbed.** The plan said "backend, model, budget and counter move together", and
three of those were already in `App`. The fourth is *derived*: a counter is
built for a model by `counter_for(model, tokenizer)`, and the tokenizer path was
consumed at startup and thrown away — so the field was there and the thing
needed to rebuild it was not. `StdioOptions::tokenizer` is a new field for that
one reason, and it is why a switch counts the new model with the new model's
tokenizer instead of the old one's.

**`destination_from` had to be computed before the struct literal, not inside
it.** `profile: name` moves the name, and the discriminator needs to read it.
Trivial, and worth the line: it is the second field in `Resolved` (after
`window_from`) whose whole content is *who said so*, and both exist because a
page is read by somebody who did not type the flags.

**A body-less `POST /api/sessions` is not `Json<NewSession>`.** Every client
written before this parameter existed posts no body at all, and `Json` answers
that with a 415 about a missing content type. The handler takes `Bytes` and
parses only when there is something to parse, so "no body" keeps meaning *the
destination this server is pointed at*.

**The suggestion is only "last used" once a session has been checkpointed.**
Creating a session writes no row — the store is written at checkpoints — so a
provider chosen and never used answers from the profile instead. That is the
right reading of *last used*, and it was not a decision the plan made: it fell
out of where the store is written, and is recorded here so the next reader does
not treat it as a bug.

**The framework evaluates the inside of a closed dialog.** `starter.provider`
inside `:if="starter"` still throws on the tick where `starter` becomes `null`,
which is eight console errors on a flow that otherwise works. Guarded with `?.`,
and the same guard applied to the providers table, which had the same noise
before this change and nobody had driven it far enough to see.

**The first-run check has to wait for a hello, and that is not a nicety.** The
deployed page is a *static twin of the read API* — recordings and JSON files,
with no server behind them — and it has no `/api/settings`. Asking on load put a
404 in the console of every visit to it, over a question that cannot apply,
because a static site has no destination to configure. The check now waits for
the socket to say hello and returns early on a page that fell back to replay,
which is also the honest reading of it: *this server* is the thing being asked
whether it knows where it sends.

### What the runs show

Against a server on `127.0.0.1:7895` with an empty scratch `LUU_HOME`, driven in
a real browser:

```text
modal open on load:            true          (nothing was clicked)
first-run banner:              "Nothing says where this machine sends."
after Save:                    no error, and the row offers "use →"
starter provider:              local
starter model (suggested):     qwen2.5-coder:7b   · the profile
models could not be listed:    shown — Ollama is not running on that box
header after Start session:    ["ollama", "qwen2.5-coder:7b-instruct"]
console/page errors:           none
```

and, on a second server with a `mock` profile, a whole turn through the chosen
destination:

```text
provider offered:              fixture
model offered:                 mock          · the provider's list
an answer arrived:             true
GET /api/providers/fixture/models → suggested "mock" (last used)
```

which is the store column answering: the suggestion moved from *the provider's
list* to *last used* because a session ran there and was checkpointed.

Over the API alone, the refusal path and the resolution:

```text
GET  /api/settings                → unconfigured true, backend mock, destination ""
PUT  /api/providers               → 200, config.toml written
GET  /api/providers/local/models  → [] with "transport: error sending request…",
                                     suggested "qwen2.5-coder:7b" from the profile
POST /api/sessions {local, …7b-instruct} → 201
GET  /api/settings                → profile local, ollama, window 8192 from the
                                     profile, unconfigured false
```

The Playwright smoke test over the assembled static site is 4 green, and it is
the test that would have caught the 404 above — the one console error the page
must not produce.

`cargo test --workspace` is 383 green, five of them new: the `DestinationFrom`
rule, a schema-2 store opening and keeping its rows, `last_model` per profile,
`unconfigured` over HTTP, and a session naming a profile the file does not have
(refused, and the destination left exactly as it was). `clippy --workspace --all-targets` is clean under
`-D warnings`.

### Still open, after this one

- **The record file's header after a switch**, as named above: unchanged, and
  now reachable by a person rather than only by a second `serve`.
- **`Config` still reads the environment rather than taking its path**, so the
  three write-and-resolve routes are driven in a browser and unit-tested, never
  tested over HTTP against a scratch file. This record added two of the three.
- **A model list is a snapshot**, read when the dialog opens.
- **Nothing offers the destination to a *resumed* session**, which runs on
  whatever the server is pointed at even when its own header names another. True
  before this change and louder after it.

## 2026-09-07 — the resumed session, closed the same day

The last line of *Still open* above — **nothing offers the destination to a
resumed session, which runs on whatever the server is pointed at even when its
own header names another** — is closed by
[`a-second-header`](2026-09-07.a-second-header.completed.md), written and built
the same day.

It closed as two things rather than one, which is why it was worth writing an
argument for instead of a patch. The feature is `POST /api/sessions/{id}/resume`
taking this record's `{ provider, model }` body, so a conversation can change
model without being retyped. The **defect** is the sentence quoted above, and
the fix for it is the same line in the stream: where the destination differs from
what the session's stream already names, a second `RecordLine::Header` goes down
— which lands on a plain resume that inherited a different destination too, and
that had been happening silently since `serve` could hold more than one session.

One thing this record decided is now visible as load-bearing: `Destination`
groups the backend, the model, the budget and the counter *because they are
decided together*. Resuming re-folds the history with the new counter, which is
only correct because the counter travels with the model rather than with the
process.

## Appended 2026-09-28: a destination nobody chose follows the file

Jesús, on reading *What this server is running* ("resolved when it started and
fixed for its lifetime"): **"cambiar de proveedor, no debería requerir
reiniciar el servidor de luu"**. Most of it already did not. `POST
/api/sessions` and the resume take a provider, and *Continue here* has moved a
conversation since this record's second half. What still needed a restart was
**the file's `default`**: a session that names none *keeps what is in place*,
so a default written after `serve` started reached nothing until the next
process.

That rule is kept for what somebody **chose**, and dropped for what nobody did.
`Resolved::named` is true for `-p`, for any flag (a server started with `-m`
over the default was told something the file does not say), and for a
provider picked for a session. A destination that is not named **follows the
file**:

- a new session that names nothing resolves `config.toml` again;
- saving a new `default` moves the live session at once, **only while it has
  no turns** and nothing is running. A session with turns stays, and
  `ProvidersView::waiting` says why. Moving a conversation to another model is
  *Continue here*, with a header of its own, and a side effect of saving a file
  is not where that should happen.

Beside it, the chat's destination tags stopped being a report. They open
every provider with the models it serves, asked of the provider, and picking
one does what the starter does: a new session when there are no turns,
*Continue here* when there are.

One cost found on the way, and it was already there: **the tests read the
`config.toml` of whoever runs them.** `edit_reread_probe` and `store_parity`
spawn `luu chat` with no `LUU_HOME`, and Jesús's own file had just gained a
default with an engine. Five probe tests failed on his machine and would have
passed on any other. Both now run under an empty state directory of their
own. The in-process servers in `serve_ws` and `stdio` are built as `named`,
because a test server that followed the file would start the runner's engine.
