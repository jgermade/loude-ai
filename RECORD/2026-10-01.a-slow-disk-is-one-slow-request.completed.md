# A slow disk is one slow request

## The problem

Two complaints from a day of use, 2026-09-30: `luu serve` sometimes freezes,
and a message typed in the chat sometimes takes a while to appear.

The log from [`2026-09-30.a-log-for-serve`](2026-09-30.a-log-for-serve.completed.md)
caught the freeze twice, and both times it began the same way:

```
20:34:18  start id=344 GET /api/icon-theme
20:34:23  WARN the async runtime has not turned … secs=5
   …       (every five seconds, nothing else served)
20:35:56  end id=344 /api/icon-theme ms=98081
20:35:56  client message kind="prompt" → turn 3 started, and nothing after
20:36:30  serve starting                          ← restarted by hand

21:48:57  start id=97 GET /api/icon-theme
21:51:25  end … ms=147289
```

Each time `/api/icon-theme` was the only request in flight, and while it was
in flight the tick stopped. No socket was read, no other request was
answered, and a prompt sent in the meantime was read only when the request
ended. That is the second answer the watchdog was built to give: not a lock
but a blocked runtime.

`get_icon_theme` did its work inline on a runtime worker: it read
`config.toml`, one `package.json` for each of the 80 extensions in
`~/.vscode/extensions` (`icons::discover`), and sometimes loaded the theme
itself. On a quiet disk that is **26 ms**. A fresh `serve` on the same machine
and the same config answered 60 concurrent requests in under 60 ms each. It
did not reproduce.

**What made it slow is not known.** One hint, not a finding:
`~/.vscode/extensions` was modified at 21:46Z, two minutes before the second
freeze, so VS Code was changing extensions at the time. The disk is 95% full.
Neither explains 147 s. And one worker stuck in a syscall should not stop a
12-worker runtime. That it did means either more was blocked than the log can
see, or the tick task was queued behind the blocked worker. Only a thread
sample taken during the freeze can tell which.

The chat's delay has two causes on the page, and both are certain:

- **The typed message was drawn only when `turn_started` came back**
  (`store.js`). A server that was slow to answer, or not turning at all,
  looked like a composer that had swallowed the text.
- **`$: engineCheck = state.turn != null ? watchEngine() : null`** runs on
  every change to `state`, and a streamed answer changes it once per token.
  Each run started a `GET /api/engine`: 1478 of them in one day's log, 40 a
  second at the peak. The poll the line was written for is one per turn.

## The proposal

1. **Filesystem work a handler cannot avoid goes to the blocking pool**
   (`off_runtime` in `serve.rs`, a `spawn_blocking` with the join error turned
   into a 500). This covers the three icon-theme routes: `GET`, `PUT` and
   the end of the import. A disk that takes 147 s now costs one request
   147 s, not the whole server.
2. **`watchTurnEngine(turn)`**, which calls `watchEngine` only when the turn
   is a new one. The reactive line still runs on every token. It just no
   longer sends anything.
3. **The prompt is on screen the moment it is sent**: `state.sending`, drawn
   as a dimmed user message after the transcript. It is cleared by the next
   thing the protocol socket says other than a `token` (`turn_started`, a
   refusal, a plan held at the gate), and by the socket closing. Each of
   those draws its own answer, so the echo never sits beside the real
   message.

## What it costs

A thread from the blocking pool per icon-theme request, which Settings makes
one at a time. Three small functions. The echo is one field and one
`<article>`.

## Rejected

- **Making `icons::discover` async with `tokio::fs`.** It moves the same
  syscalls to the same blocking pool one at a time, with more code and a
  hundred round trips instead of one.
- **A timeout on the handler.** A timeout on a future does not stop a thread
  that is stuck in the kernel. Once the work is on the blocking pool, nobody
  else waits on it anyway.
- **Keeping the prompt in `state.messages` and replacing it on
  `turn_started`.** A prompt held at the gate or refused never gets a
  `turn_started`, and the placeholder would need its own cleanup for each of
  those. A separate field that any answer clears needs none.
- **Fixing the reactive line by teaching jq79 which fields a `$:` reads.** It
  may be right someday, but it changes every reactive line on the page to fix
  one.

## Measured

A scratch `serve` on the mock, with a 60-token reply at 20 ms a token, driven
by Playwright. The same binary, with the page before and after:

| | before | after |
|---|---|---|
| `GET /api/engine` during one turn | 72 | 1 |
| send → user message on screen | 61 ms | 25 ms |

Locally the second row is noise. It matters when the server is slow, and
this run could not be slow on purpose. `icon-theme` checked by hand against
the scratch server: `GET` 200, `PUT` of a missing path 422 with the loader's
message and nothing written, `PUT` of Great Icons 200 and `[ui] icon-theme`
written. `cargo test --workspace`, `clippy -D warnings` and the 23 smoke
tests pass.

## Still open

- **The cause of the slow read.** The next freeze needs
  `sample $(pgrep -f "luu serve") 5 > .tmp/hang.txt` while it is happening.
  The log already says *which* request. Only a sample says *where* it waits.
- **Other handlers do the same thing on a smaller scale.** `Config::load` in
  `/api/settings`, `/api/providers` and the rest is one small file, and was
  left alone. If a sample shows `config.toml` itself as the slow read, those
  handlers go to `off_runtime` too.
- **The engine is logged `starting` twice at every `serve` start**, a few
  milliseconds apart. That is noticed, not investigated.

## Appended the same day: the engine that started twice

It did not. On 2026-09-30 the log shows 8 `serve starting` lines and 8
`engine process started` lines, one process for each start. What doubled was
the phase line. `Supervisor::warm` notes `starting` as soon as a session
points at the engine, so the page's clock starts at the click. The `ensure`
it spawns notes `starting` again just before it starts the process. The same
goes for `ready`: every model call runs `ensure`, and an engine that is already
answering got its `ready` logged again, 47 times in a day with 8 real starts.

`note` still writes the readiness table every time, which the page reads.
It now logs only when the state, the model or the error differs from what the
table already held (`moved`, with a test). Checked against the real engine on
this machine, a `serve` start now logs one `starting`, one `process started`
and one `ready`.
