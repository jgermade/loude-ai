# An icon theme from Settings

Jesús asked how to use *vscode-great-icons*. The answer was a line in
`config.toml` and a restart, and he would rather do it from Settings: **edit the
path there**, or **import a theme into luu's own directory with a file picker**.

## The problem

`[ui] icon-theme` is reachable only by editing TOML by hand, and it is read once
at startup ([`crate::icons`](../crates/luu/src/icons.rs), `lib.rs`). Settings →
General → Files shows the theme and says how to set it, but cannot set it.

It also breaks without telling anyone. An installed extension's directory
carries its version (`emmanuelbeziat.vscode-great-icons-2.1.121`), so the path
that works today points at nothing after the editor updates the extension, and
the tree quietly goes back to its two glyphs. That is the fallback working as
designed, and it is also a setting that rots.

## The proposal

**One view and two writes, behind the providers route's loopback rule.**

- `GET /api/icon-theme` returns:
  - what `[ui] icon-theme` says, and whether it loaded (and why not, if not);
  - `<state dir>/icon-themes/`, where imports go;
  - every theme found on this machine: that directory's children, plus the
    extension directories of VS Code, VS Code Insiders, VSCodium, Cursor and
    Windsurf, each kept when its `package.json` declares `contributes.iconThemes`.
- `PUT /api/icon-theme` with `{ "icon_theme": "<path>" | null }` writes `[ui]`
  **only if the theme loads**. A path that does not load is refused with the
  loader's own message, because a setting the page accepted and the server
  ignores is the failure `write` already refuses for providers. `null` clears it.
- `POST /api/icon-theme/import` takes the folder a browser's
  `<input type="file" webkitdirectory>` picked, as multipart, and:
  1. writes it under `<state dir>/icon-themes/<name>/`;
  2. validates it with the same loader;
  3. selects it.

  The upload goes to a temporary sibling and is renamed into place only once it
  loads, so a bad import never replaces a good one.

**Both writes apply live.** `App.icons` becomes a lock around the `Arc<Theme>`,
swapped on a successful write, so there is no restart. The manifest gains a
`revision` that moves on every swap, and the page puts it in each icon's URL.
This is not optional: icons are served `max-age=3600`, on the stated grounds
that the theme cannot change while the server runs, and those grounds are what
this removes. Without the revision, a new theme would draw the old theme's art
for an hour.

**A versioned extension path survives an update.** When the named directory
is missing and its last component is `publisher.name-<version>`, `locate` takes
the newest sibling with the same `publisher.name-` prefix. The file keeps saying
what was written, and the tree keeps its icons.

**Why an import and not only a path.** A browser is not necessarily on the
server's machine (one server, two people, two machines). A path is only
meaningful to the server, while a file picker is meaningful to whoever holds
the browser. Importing also takes the version out of the path, because the copy
under `icon-themes/` is named once and never updated behind luu's back.

### Import rules

The endpoint writes to disk, so it is strict:

- **Loopback only**, like every other write from Settings.
- **Every relative path is re-checked.** It must consist only of normal
  components: no `..`, no root, no drive prefix, no backslash. The picked
  folder's own name, which every browser puts first, is stripped.
- **Capped** at 32 MiB and 5 000 files. Great Icons is 2 MB and 317 files.
- **Named** from the picked folder, reduced to `[A-Za-z0-9._-]`. Importing the
  same name again replaces the old copy, but only once the new one loads.
- Nothing is executed or interpreted beyond the loader's JSON. The loader
  already refuses an `iconPath` that resolves outside the theme's directory, and
  that check now covers imported themes too.

## What it costs

- A new transitive dependency: axum's `multipart` feature pulls in `multer`.
  The alternative was base64 in JSON, which is a third bigger for the same
  bytes and a hand-rolled decoder for the PNGs every theme ships.
- The request body limit is raised to 32 MiB for that one route only.
- One lock read per icon request.

## Rejected

- **Server-side copy of an installed extension into `icon-themes/`.** It fixes
  the versioned path, but only for a browser on the server's machine, and the
  sibling fallback fixes the versioned path anyway.
- **A server-side file browser for choosing the theme**, like the workspace
  folder picker. That picker is deliberately bounded by the workspace, and an
  extension directory is outside every workspace. Widening it to `$HOME` for
  this one purpose would be the one surface that browses a person's whole home
  directory.
- **Vendoring a theme.** Refused in `crate::icons` already (1.5 MB, 263 files,
  and a redistribution), and nothing here changes that.

## Still open

- A theme whose JSON uses comments still fails with the parser's message, as it
  did at startup.
- Importing a `.vsix` directly: it is a zip, and the folder picker covers the
  case without a zip reader.

## Built, and what was checked

As proposed, in `crate::icons` (`discover`, `import`, the versioned sibling, a
package-less folder read through its theme JSON), in `serve.rs` (the three
routes, `App.icons` behind a lock, `revision`), in `Config::with_ui`, and in
Settings → General → Files. The panel keeps the note item 15 of
`ROADMAP/2026-09-17` put there, naming `[ui] icon-theme`. The redesign dropped
it at first, and `gate.spec.js` caught that.

- **Rust**: seven new tests in `crate::icons`:
  - a versioned path following the extension to its newest version, and an
    unrelated name still refused;
  - a folder without `package.json`;
  - `discover` keeping imports first and the newest editor version only;
  - an import landing and loading;
  - an import refusing `..`, an absolute path and a file outside any folder;
  - a bad import leaving the good one in place, with its staging directory
    removed.
- **Browser**: `settings.spec.js` gained *an icon theme is imported from a
  picked folder and drawn at once*. It drives the real `<input webkitdirectory>`
  with a one-icon theme, then checks that `config.toml` names
  `icon-themes/tiny-icons` beside the provider it must not delete, and that the
  tree's first icon is requested at `?r=1`. The suite is 17 of 18. The failure
  is the hover test that fails on the parent commit too.
- **By hand**, on a throwaway server whose `HOME` held a copy of Great Icons:
  it was found as *VS Code*; *use* drew it in the tree with no restart; an
  import of the same folder landed under `icon-themes/` and was chosen; a path
  that does not exist was refused with the loader's message, and nothing was
  written.

Two failures during the run were the machine and not the change: the load
average was 62, one `agent-core` test and one `serve_ws` test each failed once
under it, and both pass alone and in their suites (3 of 3).
