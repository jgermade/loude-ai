# A model server luu starts

Jesús asked for three things in Settings → Models. Two were fixes: the mock a
server fell back to was running but not shown as chosen, and a new provider was
an empty row in a seven-column table, which is now a form in a modal. The third
is this record:

> estaría bien que, desde settings, se pueda usar ollama/llama.cpp/etc
> directamente, a través de luu, pudiendo elegir un binario instalado o una
> copia propia de luu

Asked back, he chose: **the official release, downloaded**, for luu's own copy;
**tied to `luu serve`** for the process's life; **llama.cpp and ollama** first,
and a recommendation for something lighter.

## The problem

Every provider luu reaches is a server somebody else started. On a machine
with nothing running, the first run falls back to the mock. The fix is a
terminal:

```
llama-server -hf ggml-org/gemma-3-1b-it-GGUF --port 8080
```

That terminal has to stay open, and its command has to be remembered on the next
machine. `machines.md` has six machines, and on each of them the command is the
part that is not written down anywhere luu can read.

## The proposal

**An engine is a server luu is allowed to start.** It gets a table in
`config.toml`, beside `[provider.*]`, and a profile names it:

```toml
[engine.gemma]
kind = "llama"          # llama | ollama
binary = "managed"      # luu's own copy; a path; or absent: found on PATH
version = "b11236"      # managed only; absent is the version luu pins
port = 8080             # absent is the kind's own: 8080, 11434
args = ["-hf", "ggml-org/gemma-3-1b-it-GGUF", "-c", "8192"]

[provider.gemma]
backend = "openai"
url = "http://127.0.0.1:8080/v1"
engine = "gemma"
```

- **The profile keeps its URL.** The engine does not derive it. The page writes
  both when it adds an engine, so the destination a run prints is still one line
  of the file rather than something computed from another table.
- **A session on a profile with `engine` starts it and waits** until it answers:
  llama-server's `/health`, and ollama's `/`. The wait is bounded by
  `ready-timeout`, 120 s unless the table says otherwise, because `-hf`
  downloads the model on first use. The session creation that asked for it waits
  too, and the page says *starting*.
- **Settings has an Engines section**: status, start and stop, the last lines
  the process printed, and which binary it is.

### Which binary

The binary is one of three:

- **found**: `llama-server` or `ollama` on `PATH`, `/opt/homebrew/bin`,
  `/usr/local/bin`, `~/.local/bin`, and the Ollama app bundle on macOS.
- **managed**: a copy luu downloaded into `<state dir>/engines/<kind>/<version>/`.
- **a path**: written in the file by hand.

**From the page, a path is accepted only if its file name is the kind's binary**
(`llama-server`, `ollama`). An engine is a process luu executes with arguments,
and a page that could name any executable is a page that runs anything. The
file can name any path, because whoever edits the file already has a shell.

### luu's own copy

`POST /api/engines/<name>/install` reads the release **by tag** from GitHub's
API, picks the asset for this platform, and streams it to a `.part` file. It
checks the sha256 against the `digest` GitHub publishes for that asset, unpacks
it with the system's `tar`, and renames the directory into place. A download
that does not match is deleted and never unpacked.

| kind | tag pinned | this Mac's asset | size |
|---|---|---|---|
| llama | `b11236` | `llama-b11236-bin-macos-arm64.tar.gz` | 11.8 MB |
| ollama | `v0.34.4` | `ollama-darwin.tgz` | 160 MB |

- **Pinned by tag**, not `latest`. llama.cpp ships a build every few hours, and
  a copy that moved under the machine is the versioned-path problem the icon
  record had, with a model server instead of a theme. `version` in the table
  moves it, by hand.
- **`variant`** chooses a llama.cpp build other than the CPU/Metal one:
  `vulkan`, `cuda-12.8`, `rocm-10.0`. That is the knob the Ryzen+RTX box needs.
- **`tar` and not three crates** (`tar`, `flate2`, `zip`). It is on macOS,
  Linux and Windows 10+, and both bsdtar and GNU tar refuse `..` members by
  default. The Linux ollama asset is `.tar.zst`, which needs `zstd` installed;
  that is said where it fails rather than bundled.

### Its life

Children of `luu serve`, `kill_on_drop`. `serve` stops them on SIGINT and
SIGTERM before it exits. A terminal's Ctrl-C already reaches the whole process
group, but a `kill` from a test harness reaches only `serve`. Nothing is left
running, and nothing survives a restart; the next session starts it again.

### Who may

Starting a process is a larger authority than writing a provider, so every
engine route is:

- **loopback-bound**, `providers_editable`'s rule;
- **loopback by `Host`**, which nothing here checks today. Without it, a page on
  any domain that rebinds its DNS to 127.0.0.1 is same-origin with this server.
  Against `PUT /api/providers` that costs a config file. Against an engine it
  would be an execution;
- **JSON bodies only**, so a cross-site form post is refused before the
  handler runs, since it cannot send `application/json` without a preflight.

## What it costs

- `sha2`, already in the lockfile through `ed25519-dalek`.
- A process table in `App` and one module, `crate::engines`.
- Network, for the first time other than toward a model: the download. It is a
  button someone presses, never a fallback. `local-first` is about where
  prompts go, and a release tarball is not a prompt.

## Rejected

- **`latest`**: see above.
- **Building llama.cpp from source**: offered, and not chosen. It needs cmake,
  a compiler and minutes, which is fine for a person and a poor thing for a
  button.
- **Leaving the process running after `serve` exits**: offered, and not
  chosen. An orphan holding 6 GB of VRAM is what that would produce.
- **A URL derived from the engine's port**: the destination stops being
  readable in one place.

## Something lighter

llama.cpp is already the light one. `llama-server` is 11.8 MB, with no daemon,
no model store and no Python. ollama is llama.cpp plus a model registry and a
daemon, at 160 MB. **llamafile** is the one lighter to *carry*: one file that is
the server and the model together. But it is llama.cpp inside and lags behind
it, and the model rides in the binary, which is the opposite of choosing the
model in `args`. vLLM and SGLang are heavier: Python and a GPU. The
recommendation is llama.cpp as the default, and ollama for whoever already has
a model store in it.

## Still open

- Whether a model downloaded by `-hf` should be listed by the page. llama.cpp
  keeps its cache in `~/Library/Caches/llama.cpp`, which is not luu's to read.
- `ready-timeout` is a guess, and it is a key so it can be tuned by hand.
- Windows: the assets are named, but no machine in `machines.md` runs it.

## Appended 2026-09-28: what happened

Built as proposed, the same day, in `crate::engines`, `[engine.*]` in
[`provider.rs`](../crates/luu/src/provider.rs), four routes in
[`serve.rs`](../crates/luu/src/serve.rs), and Settings → Engines with a form in
a modal. Run end to end on this Mac against a scratch `LUU_HOME`, and not only
in tests:

- **The download** of `llama-b11236-bin-macos-arm64.tar.gz`: 11 761 043 bytes,
  digest matched, unpacked to `engines/llama/b11236/llama-b11236/llama-server`.
  The archive has no `build/bin/`, which is why the binary is searched for rather
  than assumed.
- **A session on `-hf ggml-org/gemma-3-270m-it-GGUF`** hit the 120 s limit and
  said which key moves it. `llama-server` printed nothing for 1:43 while it
  downloaded, and Hugging Face then refused the file with a 403 from this
  machine's network. The page showed `exited` and the last lines, which is the
  failure this section was built to make readable. **120 s is short for a first
  `-hf`**, and it stays a key.
- **The same engine on a local GGUF** (`-m` on an ollama blob, 4.7 GB): the
  session was created in **3.7 s**, the model answered `Hi`, and SIGTERM to
  `serve` took `llama-server` with it.
- **Refused**, each with the server's own sentence: `/bin/sh` as a binary from
  the page, a `Host: evil.example` start, and a form-encoded body (415).

One finding outside the plan: `llama-server` logs *"no API key is set and CORS
allows all origins"*. An engine luu starts is on 127.0.0.1 and reachable from
any page the browser opens, the same as one started by hand. `--api-key` in
`args` closes it, but only for the server, since luu does not send a key to a
profile without `key-file`. It is left as it is, and it is the next thing to do
here if the machine is shared.

`with_graceful_shutdown` was tried for the signal and replaced: it waits for
every connection to close, and the page holds a WebSocket for as long as it is
on screen. `serve` now returns when asked to stop, and stops its engines first.

## Appended 2026-09-28: `chat` and `stdio` start it too

Only `serve` started an engine, so `luu chat` on a profile with `engine` sent
to a port nobody had opened. It now does what `serve` does, once per run
(`engine_for` in [`lib.rs`](../crates/luu/src/lib.rs)). The handle lives as long
as the command, and dropping it stops the server. Measured on the scratch
config: `luu chat -p tiny "…"` started `llama-server` on the local GGUF, got
`hi`, and exited in 5.3 s with nothing left running.

## Appended 2026-09-28: the models already here, and nothing by hand

Two asks from Jesús. The first: **"me gustaría que liste los modelos indicando
de dónde lo saca, p.e. 'qwen3.8-27b (ollama)'"**, from ollama, llama.cpp,
Hugging Face and luu's own `models/`. The second: **"sobre los motores
descargados por luu, su arranque/parada debería ser automático"**.

**The catalog** is [`crate::models`](../crates/luu/src/models.rs). It reads four
stores where their tools put them and copies nothing:

- ollama's manifests, each resolved to the GGUF blob it names;
- the hub cache's `snapshots/`, keeping the newest revision of each file;
- llama.cpp's cache and `<state dir>/models`, as plain directories of GGUF.

A model is a **reference** (`ollama:qwen2.5-coder:7b`) rather than a path,
because the path into ollama's store is `blobs/sha256-60e05f…` and changes on
every pull. `[engine.*] model` carries the reference, and luu turns it into
`-m`.

Two findings from this machine's own stores:

- **The example model in the ask is not one llama.cpp can run.**
  `qwen3.8:27b-mlx` and `gemma4:26b-mlx` have `tensor` layers and no GGUF.
  They are listed as `mlx`, which is true, and never offered to a llama.cpp
  engine.
- **llama.cpp `b11236` downloads `-hf` models into the Hugging Face cache**,
  not its own: `models--ggml-org--gemma-3-270m-it-GGUF` appeared there during
  this record's first run. The `llama.cpp` source is kept for older builds and
  for `LLAMA_CACHE`.

**Automatic**, run end to end on a fresh `LUU_HOME` with nothing downloaded:

| step | what happened | wall clock |
|---|---|---|
| session on `local` | luu's copy downloaded, verified, started on `ollama:qwen2.5-coder:7b` | 12.5 s |
| same provider, `ollama:qwen2.5-coder:14b` | restarted on the 14b | 6.4 s |
| session on another provider | stopped: *no session sends to it* | — |

A llama.cpp engine takes the session's model when it is a reference and keeps
the table's own otherwise (`engines::for_run`), which is how choosing in the
chat moves the engine. An ollama engine never moves, because it serves
everything it has. A server on the port that luu did not start is used as it
is and never restarted.

The smoke suite gets its own stores through the tools' own variables, so the
catalog it tests is three fixture files and not the runner's disk.

## Appended 2026-09-29: an MLX engine, and which engine loads what

Two asks, then a third in the middle of the work. **"si tenemos seleccionado
llama.cpp o uno que no soporte mlx, prefiero mostrarlo deshabilitado con un
warning y un tooltip que lo explique"**. **"añadiría mlx_lm.server como motor
que ofrezca luu"**. And, before that was finished: **"qué tal
https://github.com/ddalcu/mlx-serve en lugar de mlx_lm.server? cuál rinde
mejor?"**

**ollama's MLX models, tried rather than assumed.** Each tensor of
`qwen3.8:27b-mlx` is its own blob and a valid single-tensor safetensors file,
and `config.json` and the tokenizer are named layers. So a directory of links
can present the model to an MLX server without copying 18 GB. It was built
(1199 tensor links) and handed to both servers:

- `mlx_lm` 0.31.3 refused the weights: unexpected `weight.scale` and
  `weight.global_scale`;
- mlx-serve v26.9.6 loaded all 2017 weights, said *Model ready*, and failed at
  the first matmul, `(1,17,5120)` against `(640,10240)`. The packed 4-bit
  weights were read as dense.

Both fail for the same reason: ollama quantizes these as **NVFP4 in
compressed-tensors**, and neither loader reads that format. **Only ollama
runs them**, and `LocalModel::runs_on` says so in the sentence the page shows.

**mlx-serve against `mlx_lm.server`**, on this machine, same weights
(`mlx-community/Qwen3-4B-4bit`), streaming, temperature 0, 256 tokens,
warmup discarded, median of three, two alternating rounds:

| | first token | decode |
|---|---|---|
| `mlx_lm.server` 0.31.3 | 123–128 ms | 79.1–81.1 tok/s |
| mlx-serve v26.9.6 | 31–33 ms | 89.9–91.6 tok/s |

About +13% decode and a first token four times sooner. That agrees with the
project's own chart (+26% over LM Studio against mlx-lm's +11%), which is an
M4 Max and the author's harness; this measurement is neither. mlx-serve
replaced `mlx_lm.server` before it shipped. The `pip`-into-a-venv install
written for it was deleted: mlx-serve is a native binary with a GitHub
release and a sha256, so it takes the same download path as the other two.
Against it: one author, seven months old, and a license GitHub reports as
*Other* while the README says MIT.

**mlx-serve loads GGUF too**, through an embedded llama.cpp, but it tells the
two formats apart by extension. Handed an ollama blob (`sha256-…`, no
extension) it answered `NotDir`; handed a `.gguf` link to the same blob, it
answered `Hi`. luu makes that link under `<state dir>/engines/links/`.

End to end, on a fresh `LUU_HOME`: `luu chat -p fast` downloaded mlx-serve
(72 MB, digest matched), started it on `huggingface:mlx-community/Qwen3-4B-4bit`,
answered, and stopped, in 18.4 s. With `-m ollama:qwen2.5-coder:7b` the same
engine served an ollama GGUF through the link, in 19.0 s.

The page greys out what the provider's engine cannot load. The chat's picker
shows it with ⚠ and the reason as a tooltip. The row is not a button, because
a disabled button shows no tooltip in every browser. The engine form uses
disabled options and also writes the reasons out, since a native `<select>`
does not show a tooltip on a disabled option everywhere.
