# Components of our own

Jesús likes the components of [rare-ui](https://github.com/swamimalode07/rare-ui)
and asked for two things: take them **as ideas, with our own implementation**,
and put the result in `crates/luu/ui/components/`, where **no component depends
on the rest of the app**. Settings is where it starts.

## The problem

rare-ui is 23 React components on Tailwind and Motion, installed with
`npx shadcn add`. [`luu-design.md`](../luu-design.md) §UI stack already decided
against that stack: the page is jq79 `.html` files embedded with `rust-embed`,
and `cargo build` does not need node. So nothing from rare-ui is installed or
copied. Its licence also argues for this: it is MIT plus the Commons Clause, and
it requires a visible credit link from anything that uses the components. Code
written here from a description of an effect is not that. This is a reading, not
legal advice, and it is why no source was copied.

The page also had no components in the reusable sense. Every `.html` in `ui/` is
a screen that imports `store.js`, `ui.js` or `prefs.js`. A segmented choice was
a global `.choice` rule plus the same three-line `<button>` repeated eleven
times.

## The rule for `components/`

A file in `components/` imports nothing. Everything it knows arrives as a prop
(or a slot), and everything it decides leaves as `$updateModel` or `$emit`. Its
styles are `<style scoped>`. Where it reads a page token, it gives a fallback
(`var(--accent, #2f5bbd)`), so it draws correctly on a page with none of luu's
CSS. What it cannot own, it takes through a slot: the rail's icons are the
page's sprite, and a component that wrote `#i-sliders` would depend on the page.

## The three components

| File | Idea from rare-ui | What it is |
| --- | --- | --- |
| [`segmented.html`](../crates/luu/ui/components/segmented.html) | `gooey-nav` | Mutually exclusive answers side by side. A pill behind the chosen one slides to the next on a damped curve (`cubic-bezier(.32,.72,0,1)`), the slide and not the goo. Options are strings or `{ value, label, disabled, title }`. |
| [`rail.html`](../crates/luu/ui/components/rail.html) | `bounce-sidebar` | Sections down the side. A 6px dot springs to the chosen one with a slight overshoot, and only the chosen label is at full colour. Items draw through a scoped slot. The arc the original takes is dropped: it is a path animation, and CSS transitions do not have one. |
| [`save-button.html`](../crates/luu/ui/components/save-button.html) | `delete-button`'s confirmation tick | Save, with the caller's count of changes on it. It is off at zero, because there is nothing to write. It awaits the caller's `action`, and truthy means written, so the label becomes a tick that draws itself and stays until the next change. Falsy leaves the button alone, because the caller is the one that knows what to say about a refusal. |

Two rules are shared by the pill and the dot:

- **The first placement snaps.** The transition is switched on a frame *after*
  the first measurement, so opening a section does not slide everything in from
  the edge.
- **`prefers-reduced-motion: reduce` turns the transitions off.** The indicator
  still moves, but without animation.

Both measure their own `.on` button with `$self` after `$mounted`, again on the
next frame whenever the model changes, and whenever a `ResizeObserver` reports
that a font or a wrap moved the buttons.

## Where they are used

- **General**: theme, editor (Monaco is a disabled option when it is not
  installed) and layout.
- **Resend**: the three rules. **Authority**: the two positions.
- **The modal's rail.**
- **Save** in Models, Resend and Authority, each with its own count:
  - Resend and Authority count the fields that differ from the file.
  - Models counts the profiles added, removed or edited, plus one if the default
    moved. It compares what would be *written*, so a nameless row, which the
    write drops, is not a change.

The three `.choice tiny` in `app.html` (the gate's network and enforcement, and
Manual/Auto) are outside Settings and are unchanged. They keep the old global
rule.

## What was checked

`tests/smoke/settings.spec.js` and `gate.spec.js`, under `gate.config.js`
against a debug `luu serve`: **17 of 17 pass**. They needed three selector
changes (`.choice` became `.seg`), and `settings.spec.js` gained two assertions:
the count reads `1` after one change, and `button.save.saved` is visible after a
save. Driven separately in headless Chromium: the pill caught halfway between
*Light* and *Dark*, *Save 2* after two changes, back to plain *Save* when both
were undone, the dot at each section, and no console output from jq79.

The first full run failed on two gate tests with *an effect re-woke itself 100
times*. Models' count built the file's side with `toDraft`, which does
`++rowId`, so the effect wrote what it read. `toDraft` now takes the id function
as a parameter, and the count passes one that writes nothing.

Not checked: reduced motion (not emulated), Firefox and Safari.

## Rejected

- **Installing the components** (React islands, or a committed build): this is
  the §UI stack decision, and nothing here argues with it.
- **A global `slide.js`**, which is what was built first, earlier the same day.
  It was one module that watched the whole document with a `MutationObserver`
  and drew the indicator with CSS under a `data-slid` attribute, so no template
  changed. It worked and it was checked, but it was the opposite of the rule
  above: behaviour that attaches itself to any element with the right class name
  is a dependency on the whole page, in both directions. It was never committed.
- **`delete-button` for Models' `remove`**: that removes a row from an unsaved
  draft, and nothing is written until Save. The page's one irreversible delete,
  a session, already confirms in place.

## Later the same day: the rest of the page, highlighting, and Monokai

**Every `.choice` is now a `Segmented`.** The three in `app.html` moved: the
gate's *network* and *enforcement* (whose values are `null`, `true` and
`false`, so the component keys buttons by `String(value)`) and the composer's
*Manual / Auto*. The global `.choice` rule and `.choice.tiny` are deleted.
`tiny` is `size="small"`, with the same metrics.

**Highlighting had three holes, not one.** Asked for `.md`, measured on this
repository through `/api/workspace/file`:

| File | Before | After |
| --- | --- | --- |
| `AGENTS.md` | 156 punctuation chunks and nothing else | headings, strong, emphasis, links, code spans, and fenced blocks in their own language |
| `editors/vscode/src/extension.ts` | 2 keywords | 42 keywords, plus strings, functions and operators |
| `app.html` | `<script>` and `<style>` as plain text | JavaScript and CSS inside them |

The causes:

- **Markdown's captures are prose names** (`text.title`, `text.literal`,
  `text.uri`, `text.reference`, `text.emphasis`, `text.strong`). None was in
  `NAMES`, so they are listed now, and `class_of` maps each to a one-word class
  (`heading`, `literal`, `link`, `emphasis`, `strong`) with its own CSS.
- **Injections were off** (`|_| None`). They are on, through `injected`, which
  resolves a grammar's name or the name read as an extension, so a fence can say
  `rust` or `rs`.
- **TypeScript's query is only TypeScript's additions.** It is now its own
  followed by JavaScript's, and TSX also takes JavaScript's JSX query, the way
  the grammar inherits.

**Markdown's inline half would not highlight as an injection.** With injections
on, the block grammar injected `markdown_inline` into every `inline` node, the
callback returned the grammar, and the layer produced no highlights. Checked:

- the inline grammar parses correctly with the same included ranges;
- it highlights correctly as a top-level language;
- injected through a fence instead, it is empty again.

So the fault is the inline grammar as an injected layer in
`tree_sitter_highlight` 0.27, and patching a dependency was not the fix. It is
instead a second pass, only for Markdown: the block pass, then each `inline`
node's text highlighted on its own and laid over it wherever it has a class. A
test pins that the chunks still join back into the file through multi-byte text,
a block quote and a fence. One approximation is written down where it happens:
a block quote's `> ` markers sit inside the `inline` node and are read as text,
which is also what they were before.

**Monokai is a second set of colours, and the palette's own comment argues
against one.** That comment's reason is that the viewer follows the light/dark
toggle for free and there is one palette to argue about. It still holds for the
default, which is unchanged: the new `code` preference (`page` | `monokai`,
`localStorage` like the other facts about the screen) defaults to `page`.
Monokai is opt-in because it was asked for by name.

- It sets `data-code-theme` on `<html>`. One block of `--hl-*` overrides under
  that attribute recolours every `.hl-*`, and the content column and
  `.code-rows` take Monokai's `#272822` ground.
- **The ground is not decoration.** Its yellow (`#e6db74`) and green (`#a6e22e`)
  are unreadable on the light page, and a code theme that only works on one page
  theme would be a second toggle hidden inside the first.
- Monaco gets `luu-monokai`, written out rather than read off the stylesheet,
  because it is the one theme that is not the page's.
- The control is Settings → General → Editor → *Colours*.

**What was checked:**

- `cargo test -p luu`: all pass, including six new highlighter tests (Markdown
  classes, a fence under two names, TypeScript and TSX, `<script>` in HTML, every
  grammar compiling, and the Markdown round-trip).
- The live-server smoke suite: 16 of 17. The one failure is *the tree shows an
  edit icon on hover*, which fails 2 in 4 runs on the parent commit's UI as well.
  It is a flake that predates this, not a regression, and it is still open.
- Screenshots on a throwaway `luu serve` (its own `HOME`): `AGENTS.md` under the
  page palette and under Monokai, and `luu-design.md` under Monokai on the light
  page. No console output.
- Not checked: Monaco under Monokai, because Monaco is not installed on this
  machine.

## Appended 2026-09-29: a fourth, `dropup.html`

[`dropup.html`](../crates/luu/ui/components/dropup.html) holds a choice that
opens upward. The current answer sits on a button, and each option has the
line that says what it means under its label. It has the same contract as
`Segmented` (`options`, `model`, `$updateModel`, `change`), so either fits a
tag. It is not from rare-ui. It follows this file's rule for `components/`:
it imports nothing, and every colour has a fallback.

Its first use is the gate's *Manual* / *Auto* in the chat's foot, which was a
`Segmented` and took the width the destination needed. The menu is
`position: fixed`, measured from the button and kept inside the window,
because a status bar clips what overflows it. Escape closes it from anywhere
while it is open, and the arrow keys move through the options. See
[`what-a-day-of-use-found-on-the-page`](2026-09-29.what-a-day-of-use-found-on-the-page.completed.md).

## 2026-09-30: a border instead of a dot, and a Settings that moves

Jesús asked for three changes to the Settings modal and then a fourth.

- **`Rail` marks the chosen section with a border, not a dot.** The rail has
  a 1px line down its left edge. A 2px stretch of it in the accent colour, the
  chosen item's own height, springs to the item with the same curve the dot
  had. A border stands beside the whole item where a dot stood beside its
  middle. The component's contract (`items`, `:model`, `change`, the slot) is
  unchanged, and it is still self-contained.
- **Engines before Models.** A provider can name an engine, so the thing it
  names comes first.
- **Resend and Authority are one section, Sessions** (`settings-sessions.html`).
  Both halves answer one question, what a session is rendered under beyond
  what was asked, and both are the session's own choice recorded in its
  header. Each stays its own component with its own save, because each writes
  its own table of `config.toml`. The smoke tests that drove them now click
  *Sessions*, are scoped to `#sessions-resend` and `#sessions-authority`, and
  assert the rail's order.
- **A change of section is a transition.** The old content fades out (140 ms),
  the new one is put in and fades in (200 ms), and the pane's height follows
  its content (240 ms), measured by a ResizeObserver rather than once. Most
  sections fetch their data in their own `:setup` and grow after they appear,
  and a height measured at the switch would have jumped at the end. The height
  is capped at what `max-height: calc(100vh - 6rem)` leaves the pane, past which
  it scrolls as before. Measured in a browser switching General → Engines: the
  dialog went 804 → 458 → 340 → 330 px while the content's opacity went 0.81 →
  0.12 out and 0.10 → 0.63 → 1 in. Four clicks in quick succession land on the
  last one only. The section on screen (`shown`) trails the chosen one
  (`ui.section`) by the fade. The rail answers the click at once, and the pane
  follows.

## 2026-09-30, later: no line, a transition that knows its end, and modals that move

- **`Rail` loses the line.** The 1px border that joined every section is
  gone. Only the accent bar beside the chosen one remains, springing to it as
  before.
- **Settings' height, done again.** The first version faded out, swapped,
  and followed the new section's height with a ResizeObserver. Most sections
  fetch their data in their own `:setup`, so the height moved twice: once on
  the swap, again when the data landed. Jesús: "it does something odd, it is
  not smooth". Knowing the next height before animating is the fix. The chosen
  section is now mounted invisible and loads, its height is watched per frame
  until it has not changed for 90ms (700ms at most), and only then does the
  pane's height go to it, in one motion, while the old section fades out and
  the new one fades in. Sampled per frame from General to Engines: about 130ms
  of preparation, then 854 → 595 → 385 → 341 → 331 → 330px. A version that
  mounted all four sections at once, so every height was always known, was
  built and dropped the same hour: a section mounted since the modal opened
  goes stale. A provider added from Engines did not appear in Models, which
  the smoke suite caught. Sections are mounted per visit again, the old one
  kept only for its fade.
- **Every modal opens and closes animated.** `dialog.modal[open]` plays
  `modal-in` (a few pixels up and 2% of scale, 200ms) and its backdrop fades
  in. Closing is `modal.js`'s new `closing(id, done)`: it adds `.closing`,
  which plays `modal-out` (140ms), then calls the page's own close, which
  unmounts it. Every modal's close function goes through it (settings, the
  starter, the folder picker, the turn and context modals, the provider and
  engine forms, their saves included). `cancel` is always refused now and
  routed to the same close, because the browser would otherwise close the
  dialog at once and skip the animation. Measured: ESC leaves the dialog on
  screen 149ms with `.closing`, then it is gone.
