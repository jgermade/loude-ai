# Runtimes, and the machines they run on

## The question

A session on the `colima` variant failed at its first tool call:

```
the colima (luu-worker:dev) worker: the worker said nothing before it was
asked: the worker exited (exit status: 1): time="…" level=fatal
msg="colima is not running"
```

`colima list` had no instance at all, so the fix was not "start it". It was
"create a VM with containerd, then build the image inside it", because
colima's containerd shares no images with Docker. Looking at that, Jesús:

> por lo que veo, colima es más un proveedor de runtime que un runtime

He is right. This record says what follows from that, before any code.

## What is true today

`Runtime` has five contained values: `docker`, `podman`, `nerdctl`,
`container` and `colima`. They are offered side by side, as the
`[worker] runtime` of a policy file and as the variants of a contained
posture
([`the-terminal-follows-the-session`](2026-10-01.the-terminal-follows-the-session.completed.md)).
Four of them are a command-line tool that luu builds `run`, `exec`, `build`
and `image inspect` for. The fifth is not:

- **Colima runs no containers.** It is a Linux VM, on Lima, that hosts a
  runtime: Docker's daemon or containerd. `Runtime::Colima` means "`nerdctl`,
  inside colima's VM". That is why it is the one special case in
  `Runtime::invocation`, which prefixes it with `colima nerdctl --`.
- **The code already knows this in one place.** `Runtime::Docker`'s
  `install_hint` says "Docker Desktop, or `brew install colima docker` and
  `colima start`". That is colima as a place for docker to run, which
  `Runtime::Colima` cannot express.
- **The runtimes record mixes the two levels.** In
  [`runtimes-in-settings`](2026-10-01.runtimes-in-settings.completed.md),
  condition (2) reads "it answers, meaning Docker's daemon is up, Podman's
  machine is running, Colima is started". A daemon, a VM and a VM: two of
  the three things it names are where a runtime lives, not runtimes. The
  same record says "each runtime keeps its own store", and that is only
  roughly true. The docker CLI pointed at Docker Desktop and the docker CLI
  pointed at colima are one runtime with two stores. **The store belongs to
  the machine**, and today's failure was exactly that.

The same split exists for the others, unnamed:

| runtime (what luu speaks) | where it can run |
| --- | --- |
| `docker` | Docker Desktop, OrbStack, colima (docker), Rancher Desktop (moby), a Linux daemon |
| `podman` | a `podman machine` (macOS), or native (Linux) |
| `nerdctl` | colima (containerd), Rancher Desktop (containerd), Lima, native containerd (Linux) |
| `container` | Apple's own service, nothing else |

## The proposal

**Two words, not one.** A *runtime* is the CLI luu builds argv for:
`docker`, `podman`, `nerdctl` or `container`. A *machine* is where that
runtime's daemon and store live, and it is optional. With no machine, a
runtime uses whatever its CLI uses by default, which is what every run
before this has done.

```toml
[worker]
runtime = "nerdctl"
machine = "colima"        # optional: the CLI's own default without it
image = "luu-worker:dev"
```

A machine is never a URL or a socket the page could type. It is a name the
runtime's own CLI already knows, and it becomes that CLI's own flag, as the
first words of every argv:

| runtime + machine | argv prefix |
| --- | --- |
| `docker` + a context (`colima`, `orbstack`, `desktop-linux`) | `docker --context <name>` |
| `podman` + a connection (`podman-machine-default`) | `podman --connection <name>` |
| `nerdctl` + `colima` | `colima nerdctl --`, or `colima --profile <p> nerdctl --` |
| `container` | no machine |

This keeps the argument that made `Runtime` "a name rather than an
integration". luu still speaks no runtime's API. The machine only changes
the first words of a line luu already writes.

**What it changes:**

- **`Runtime::Colima` goes, and the word stays readable.**
  `runtime = "colima"` in a policy file loads as `runtime = "nerdctl"`,
  `machine = "colima"`, with a warning naming the new spelling. No
  `config.toml` and no policy file stops loading.
- **A variant is a runtime on a machine.** The picker offers each contained
  posture on each pair that *answers*, not on each runtime compiled in.
  `docker · colima` and `docker · desktop-linux` are two entries, because
  they are two stores. The rule from the terminal record stays: the browser
  picks from a list luu wrote, and never types a runtime, a machine or an
  image.
- **Settings → Runtimes becomes two lists.** The runtimes say whether the
  CLI is installed. The machines say whether the machine exists and is
  running, which runtime it serves, which images its store has, and offer
  *create*, *start* and *build* by the same rules as today: Homebrew and no
  root. The machines are found by asking each CLI, not by guessing:
  `docker context ls`, `podman system connection ls`, `colima list`.
- **The images question moves from runtime to machine**, so "missing" is
  said about the place that is missing it. Today's failure would then have
  read "colima: no instance — create it" in Settings, before any session
  tried.
- **A worker that will not start names the machine.** The error today
  ends in colima's own `level=fatal` line (stderr reaches the message since
  2026-10-02). With a machine it can also say which one, and point
  at Settings.

## What it costs

- **The `Runtime` enum is in recordings.** A verdict names its worker as
  `colima (luu-worker:dev)`. Old recordings keep saying that; new ones say
  `nerdctl@colima (luu-worker:dev)`. A reader of both has to know they are
  the same thing. Recordings are append-only, so this is a note in the
  design doc, not a migration.
- **The variants list grows and becomes a probe.** Today it is a constant
  (`Runtime::CONTAINED`). After this, it depends on what `docker context ls`
  and the others answer, so `/api/postures` costs a probe, or reads the last
  one Settings ran. It should read the last one. Probing on every picker
  open was rejected in the runtimes record for good reason.
- **Four argv shapes to test instead of one.** Each `--context` /
  `--connection` / `colima nerdctl --` prefix is a new line in the tests
  that pin argv, and needs a run against the real thing. Only docker and
  colima are on this machine. Podman machines and OrbStack would be written
  from their documentation, as Apple's `container` was.

## Rejected

- **Keep `colima` as a runtime and add `colima-docker`.** That makes the
  list a product of the two axes, written by hand. It also still could not
  say "docker on OrbStack".
- **A `DOCKER_HOST` / socket path per posture.** That is a URL in all but
  name, so the browser would be one field away from typing where commands
  run. It also does not work for `podman` or `colima nerdctl`, whose
  machines are not sockets the CLI is pointed at that way.
- **Leaving it, and fixing only the message.** The message is fixed (see
  above), and the model is still wrong in the way that produced the
  failure: Settings could not have said "colima has no instance", because
  it asks "is colima answering" about a runtime that has no instance to
  answer.

## Still open

- **The word.** `machine` is podman's term, and it fits a VM better than a
  Linux daemon. The obvious alternatives are taken: `host` is
  `Runtime::Host`, which means *no container*; `provider` is a model
  provider (`[provider.<name>]`); `engine` is a model server
  (`[engine.<name>]`). `place` is what the terminal says (`host` /
  `container`) and means something else again. `machine` is the least
  taken.
- **Whether a machine belongs in the policy file or in `config.toml`.** The
  runtime is in the policy file today, since it is part of "where commands
  run". A machine is more a fact about this computer than about the
  sandbox: the same policy on another laptop has another docker context.
  That argues for `config.toml`, as `[posture.<name>] machine = …`. The
  policy file would then name a runtime and stay portable.
- **Rancher Desktop and Lima** are in the table and not in the proposal's
  argv list. Each is one more prefix, and neither is installed here.
