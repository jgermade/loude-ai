# Columns that are dragged

## The problem

The inspector was 20rem wide and the chat 30rem, fixed in the grid. A tree
with deep paths and a chat with long answers want different widths on
different days, and the page had no way to give either one more room. The
two-column pin in General was the only lever, and it is a different answer:
it removes a column rather than moving an edge.

## What was built

An edge to drag on each column with a width of its own: the inspector's right
edge and the chat's left edge. The content column is the grid's `1fr` and
takes whatever is left.

- **The widths are CSS custom properties on `.app`** (`--inspector-w`,
  `--chat-w`), and the grid clamps them against the window:
  `clamp(180px, var(--inspector-w, 20rem), 35vw)` and
  `clamp(280px, var(--chat-w, 30rem), 50vw)`. The script says how wide
  somebody asked for, and the stylesheet says how wide the window allows. A
  width dragged on a wide screen therefore gives way on a narrow one without
  being forgotten, and comes back when the window does.
- **A drag writes the property and nothing reactive.** Pointer moves come
  sixty a second, and a write to `prefs` wakes every line that read the store
  (see the jq79 note in
  [`2026-10-01.the-page-in-web`](2026-10-01.the-page-in-web.completed.md)).
  The width goes to `prefs` and `localStorage` once, on release, and only if
  it changed. So the two pointer-downs of a double click save nothing.
- **Kept with the screen's other facts**: `luu.width.inspector` and
  `luu.width.chat` in `localStorage`, beside the theme and the layout, for the
  same reason as those. A width belongs to a screen, not to a run.
- **Double click resets** to the stylesheet's width and forgets the kept one.
  **Arrow keys** move a focused edge 16px the way the arrow points. The edge
  is a `role="separator"`, and a control a mouse can work, a keyboard can too.
- **In two columns** only the inspector's edge exists. There the chat is the
  `1fr`, and an edge that moved nothing would be a lie.
- The handle is an 8px strip over the border, drawn only on hover and focus,
  so it takes nothing from the layout. During a drag, `html.resizing` holds the
  cursor and stops text selection over whatever the pointer crosses.

## Checked

Playwright on a scratch server at 1440×800. Starting at 320/640/480
(inspector/content/chat):

| step | inspector | content | chat |
|---|---|---|---|
| inspector edge +120px | 440 | 520 | 480 |
| chat edge −150px | 440 | 370 | 630 |
| reload | 440 | 370 | 630 |
| inspector edge +2000px | 504 (35vw) | 306 | 630 |
| double click | 320 | 490 | 630 |
| 3× → | 368 | 442 | 630 |
| window 1270px | 368 | 272 | 630 |

At 1000px (two columns) the inspector kept its width and there was no chat
edge. No console errors. The live smoke suite passes, 23 of 23, against a
release binary rebuilt with the change.

## Rejected

- **Widths in `config.toml`.** They are facts about a screen, and one server
  answers two screens.
- **Resizing the content column too.** It is the remainder. A third edge would
  give two of them for the same boundary.
- **Clamping in the script only.** A width kept at 600px on a 2560px screen
  would squeeze the content column to nothing on a laptop. The window can
  change after the drag, and only the stylesheet sees it change.

## Still open

- **The content column has no floor of its own.** It is whatever 35vw and
  50vw leave, which at 1270px with both columns at their widest is about 15%
  of the window. Wide enough to read, but not by much.
- Touch works through pointer events and was not tried on a device.
