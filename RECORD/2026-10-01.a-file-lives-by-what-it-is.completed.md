# A file lives by what it is

## The problem

`web/` was flat: 37 files side by side. Component names carried their
place on screen as a prefix (`inspector-files`, `settings-general`), and the
modules sat beside the components that use them. Nothing in the tree told a
component that composes the page from one any part of the page can use, or a
store from a pure function.

## The convention

Jesús's, from this day:

- **`views/`** holds the components that compose the view: one folder per
  view, nested as the screen nests them (`views/inspector/tree/`,
  `views/settings/general/`). The file is named after its folder
  (`tree/tree.html`, chosen over `index.html` so a tab or a search result
  says which view it is). Parts only one view uses go beside it:
  `folder-picker.html` in `tree/`, `provider-form.html` in `settings/models/`,
  `rows.js` and `monaco.js` in `editor/`.
- **`components/`** holds the components any view may use. They import
  nothing from the page (`segmented`, `rail`, `save-button`, `dropup`), as
  [`2026-09-28.components-of-our-own`](2026-09-28.components-of-our-own.completed.md)
  already required.
- **`lib/`** holds shared modules that keep state or depend on something
  outside themselves: a store, the API, the DOM, `localStorage`.
- **`helpers/`** holds files of functions that keep nothing and depend on
  nothing but other helpers, such as a format converter.

## Where each file went

| was | is | why there |
|---|---|---|
| `inspector-files.html`, `folder-picker.html` | `views/inspector/tree/` | the tree, and the folder it is rooted at |
| `inspector-git.html` | `views/inspector/version-control/version-control.html` | |
| `inspector-debug.html` | `views/inspector/debug/debug.html` | the inspector's third panel, not in the sketch |
| `content-viewer.html`, `rows.js`, `monaco.js` | `views/editor/` | the two modules draw only this view |
| `tool-call`, `model-picker`, `session-starter`, `turn-inspect`, `context-modal`, `context-view` | `views/chat/` | the chat's parts; the column itself is still in `app.html` |
| `settings-modal.html` | `views/settings/settings.html` | |
| `settings-{general,models,engines,sessions}.html` | `views/settings/<name>/<name>.html` | with `provider-form` and `engine-form` beside their section |
| `settings-resend.html`, `settings-authority.html` | `views/settings/sessions/` | parts of Sessions, which is all they are shown in |
| `store`, `ui`, `prefs`, `workspace`, `engines`, `modal`, `resize` (`.js`) | `lib/` | state, `fetch`, DOM or `localStorage`, each of them |
| `segments`, `timing`, `prompt-parts` (`.js`) | `helpers/` | no imports, no DOM, nothing kept |

**The move rewrote imports by resolving each one, not by search and
replace.** Every relative specifier in every file was resolved against the
file's old place, looked up in the move table, and written relative to the
new one. A check after the move found every import pointing at a file that
exists, except four: `lib/*.js` importing `./vendor/jq79.js`, missed because
`vendor/` was left out of the table, and fixed by hand. `fetch("./api/…")` and
Monaco's `./vendor/monaco` were left alone. They resolve against the
document, not the module, and the move does not change them.

Old names in comments, in `luu-design.md` and in the Rust were updated. The
records were not: they say what was true when they were written. The
protocol test reads `web/lib/store.js`. Two smoke tests imported
`./workspace.js` from the page and now import `./lib/workspace.js`.

## Checked

A browser on a scratch server: the three inspector panels, a file opened,
and the four settings sections, with no console errors and no 4xx. Then the
live smoke suite against a rebuilt release binary (23 of 23) and the static
twin's (5 of 5).

**One run failed two tests, and the move was not why.** On the first launch
of the freshly built release binary, the first `GET /api/icon-theme` took
**39 s**. After that it took 8 ms. Settings → General still said *asking the
server…* when the two tests that read the icon rows looked. This is the slow
read of
[`2026-10-01.the-page-in-web`](2026-10-01.the-page-in-web.completed.md),
caught this time on a build that had just been made, which is the third time
it has followed a fresh binary. A second fresh build, made to sample it, did
not hang. The suite passed on the next run.

## Still open

- **The chat column is not a view yet.** It is about 400 lines of
  `app.html`, together with the state it shares with the gate and the
  composer. `views/chat/` holds its parts and not the column itself. The same
  goes for the inspector's and the content column's heads.
- **Pure functions still live in stateful modules**: `foldTranscript` in
  `lib/store.js`, and `modelLabel`, `defaultPort` and `profileFor` in
  `lib/engines.js`. By the rule above they are helpers. Moving them out is a
  refactor, not a move, and was left for one.
