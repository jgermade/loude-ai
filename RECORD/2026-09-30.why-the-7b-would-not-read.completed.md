# Why the 7B would not read the project, and what was changed for it

Completed the day it was written: a diagnosis, one change to a machine's
configuration, and two proposals that are not built.

## What happened

After native tool calls were built
([`native-tool-calls`](2026-09-30.native-tool-calls.completed.md)), Jesús
spent a session asking `qwen2.5-coder:7b` to find out what the project is.
Across eleven turns it:

- answered from nothing, where the answer needed a tool ("I have no way to read
  files outside this conversation");
- reached for `src/main.rs` four times: `read_file src/main.rs`,
  `read_file crates/src/main.rs` twice, `list_dir src`. None of those paths
  exists in this repository;
- listed the root correctly (`list_dir` with no path returned `AGENTS.md`,
  `Cargo.toml`, `crates/`, …), and then invented `crates/src/main.rs` out of
  that listing;
- repeated its own earlier sentences word for word ("Could you give me the
  full path to the file?", three times).

## What it was

Read off the live server (`/api/settings`, `/api/sessions/live`):

1. **The session was still on the fenced transport** (`tool_calls:
   "fenced"`). The profile had not been given `tool-calls = "native"`, so the
   model was reading our preamble, whose one example is `{"name":
   "read_file", "arguments": {"path": "src/main.rs"}}`. That example is where
   every `src/main.rs` came from. The same preamble is what 7/15 was measured
   under, against 15/15 native, on this same server.
2. **The model had no map of the tree** (`map_tokens: 0`, `select_tokens:
   0`), so every path it named was a guess. A correct listing was not enough
   to stop it guessing.
3. **A 7B.** The session's own history kept its mistakes, and a 7B rereading
   them repeats them.

The window was not a cause. It had just been learned from the server (32 768,
[`the-window-the-server-says`](2026-09-30.the-window-the-server-says.completed.md)),
and the longest prompt in the session was 4 047 tokens, summed over two calls.

## What was changed

On Jesús's machine, with his yes: `tool-calls = "native"` added to
`[provider.llama_cpp]` in `~/.config/luu/config.toml`, the previous file kept
aside. Checked by a run that prints `provider: llama_cpp →
openai@127.0.0.1:8080, tool calls native` and `window: 32768, from the
server`. A new session picks it up without restarting `serve`, because a
session whose destination follows the default re-reads the file.

Advised and not done here: `--map-tokens 2048` now that the window is known,
a new session so the history's mistakes stay behind, `qwen2.5-coder:14b` (on
the machine, measured in
[`the-14b-tool-call-probe`](runs/2026-09-15.14b-tool-call-probe/)), and asking
one step at a time with paths named. `list_dir` lists one level, so "read the
tree two levels deep" is several calls, which a 7B chains badly.

## Still open

Two changes to luu itself, each of which changes what every run sends and so
needs its own record before it is built:

- **The system prompt names the project root** and tells the model to list or
  read before stating anything about a file. It is one sentence in the cached
  prefix, aimed at the "I cannot read files" answer and at invented paths.
- **`list_dir` takes a `depth`**, so "two levels" is one call rather than a
  chain a 7B does not finish.

## The freezes, for the same day's record

`luu serve` froze twice on 2026-09-30 after Settings was opened. The first
time the cause was found and was mine. The page and the server disagreed on
`record::FORMAT` (18 against 19) partway through the native work, the server
refused the page's `hello`, and a refused page does not retry. It was fixed
by moving the page to 19. The second was measured (0% CPU, every endpoint
timing out at 5 s) and not explained, because the process was closed before a
thread sample was taken. It led to
[`a-log-for-serve`](2026-09-30.a-log-for-serve.completed.md), whose watchdog
names a request that never finishes and says whether the runtime stopped
turning. A reactive loop found later in the page
([`the-foot-and-the-turn`](2026-09-30.the-foot-and-the-turn.completed.md),
"The reactive loop, found") could make a page look frozen, but not a server
at 0% CPU, so it is not taken to be the second freeze. That one stays open
until the log catches it.
