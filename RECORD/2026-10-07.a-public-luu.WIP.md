# A public luu

## The question

Jesús, on 2026-10-07, after the project modal made a second `luu serve`
reachable from the page:

> va a ser público de verdad, estoy pensando en desplegarlo con docker o helm

> qué tal una identidad si es docker y varias si es helm o kubernetes?

> estaba pensando en usar email y passkeys

> la cuestión es que debe ser configurable, publico o privado, servidor o
> cliente, etc

Asked where tools run and which model: **in the server's own container**, and
**the model is configured as it is locally**.

## What is true today

- **Two exposures, chosen by the address.** Loopback is unauthenticated.
  Anything else needs `--auth-token-file`: one bearer token, which the browser
  carries as `/?token=…` in the URL, so the token ends up in the history and
  in every proxy's log.
- **Everything that outlives a session is loopback-only.** That covers
  providers, engines, hosts, the icon theme and the host shell. Off loopback,
  Settings can be read and not written. The rule is right for a token, because
  a token answers *who can reach the port* and not *who owns this machine*.
- **One live session per `serve`** (roadmap #14).
- **Tools run where the posture says.** On a laptop that is a docker
  container luu starts. In a container luu is already in, that would mean the
  host's docker socket, which is root on the node.
- **A server can already be a client.** `[host.<name>]` forwards
  `/h/<name>/…` to another `luu serve` with that host's token
  ([`a-project-is-a-host`](2026-10-02.a-project-is-a-host-a-folder-and-a-session.completed.md)).

## The proposal

### Every axis is a key, and none is a deployment

Not "a docker mode" and "a helm mode". Docker and Helm are two ways of
writing the same `config.toml`, and both end up as these keys:

```toml
[server]
# loopback | private | public
#   loopback: today's default, no authentication
#   private:  off loopback, a bearer token (today's --auth-token-file)
#   public:   identities with passkeys; bearer tokens only as an identity's
#             API tokens, never in a URL
exposure = "public"
bind = "0.0.0.0:7878"
# What a browser types — the WebAuthn origin, and what Origin is checked
# against. Required for public: behind a proxy, luu cannot know it.
origin = "https://luu.example.com"
# What this server does: run sessions here, and/or forward to hosts.
# ["sessions"] a worker pod, ["hosts"] a front door, both: today.
roles = ["sessions", "hosts"]

[auth]
session-hours = 168          # the cookie's life
# Optional: without SMTP, an invitation is a link printed by `luu auth invite`.
[auth.smtp]
url = "smtps://smtp.example.com:465"
from = "luu@example.com"
password-file = "/run/secrets/smtp"

[identity.jesus]
email = "jesus@germade.dev"
owner = true                 # may write Settings off loopback
hosts = ["jesus"]            # on a front door: where this identity may go
```

Every key is optional and has a default that is today's behaviour, so a
`config.toml` with none of them is the laptop that exists now. Flags and
`LUU_*` variables override for one run, the way `--bind` does now, because a
container is configured by its environment first.

### Public means identities, and identities mean passkeys

- **Enrolment is an invitation.** `luu auth invite <email>` writes a one-time
  link, valid for an hour. With `[auth.smtp]` it emails the link. Without
  SMTP it prints the link, which is enough for one person:
  `docker exec luu luu auth invite me@…`. Opening the link enrols a passkey on
  that device. **Recovery is the same act**: a new invitation and a new
  passkey. There are no passwords to reset.
- **Login is a discoverable passkey.** No username field: the browser offers
  the passkeys it has for the origin. The email is the identity's name and
  where invitations go, and never a password.
- **A login is a cookie**, `HttpOnly; Secure; SameSite=Strict`. The socket
  sends it on the upgrade, as a browser always does to its own origin, so
  `?token=` stops being how a browser authenticates. **`Origin` is checked on
  every socket and every write**: a cookie is sent by any tab, and `Origin` is
  what tells this page apart from another site's.
- **Credentials are data, not configuration.** Passkeys, invitations and live
  logins go in `auth.db` in the state directory, beside `sessions.db`.
  `config.toml` says *who* may log in, and the database says *with what*.
- **API tokens are an identity's, and named.** A laptop that reaches this
  server as `[host.public]` presents a token minted for an identity
  (`luu auth token jesus --name laptop`). It is listed and revocable, and it
  carries only that identity's authority.

### What an identity may do

- **`owner = true` is what loopback was.** The Settings writes that are
  loopback-only today become *loopback, or an owner's passkey login*. Never a
  bearer token, for today's reason. So an owner can configure a public
  server's providers from the browser, as on a laptop.
- **An approval is still an approval.** Signed approvals stay what they are.
  An identity's login can carry its own key later. That is a later record.

### Server or client: roles

`roles` says what a process does:

| roles | what it is | example |
| --- | --- | --- |
| `["sessions", "hosts"]` | today: sessions here, and other hosts through `/h/` | the laptop |
| `["sessions"]` | sessions only, behind someone else's door | one identity's pod in Kubernetes |
| `["hosts"]` | a door: logins, and `/h/<host>/` to the hosts an identity may reach | the public front in Kubernetes |

A door keeps identities and forwards. It keeps no sessions, so *a session
stays on the host that made it* still holds. A door is **not** the portal
rejected in
[`the-portal-and-the-gate`](2026-08-31.the-portal-and-the-gate.completed.md):
that portal kept a session index and moved sessions. A door keeps a list of who
may go where, and its traffic is the `/h/` proxy that already exists.

### Docker: one identity

One container, `exposure = "public"`, roles `["sessions", "hosts"]`, one
`[identity]` with `owner = true`:

```yaml
# deploy/compose.yaml
services:
  luu:
    image: ghcr.io/jgermade/luu:latest
    environment: { LUU_HOME: /state }
    volumes: [state:/state, work:/work]
    working_dir: /work
  caddy:                     # TLS; WebAuthn needs https
    image: caddy:2
    command: caddy reverse-proxy --from luu.example.com --to luu:7878
    ports: ["443:443", "80:80"]
```

### Helm: several identities

- **A door**: a `Deployment` with roles `["hosts"]`, behind the `Ingress`
  (TLS through cert-manager), holding `auth.db`.
- **A pod per identity**: a `StatefulSet` per entry in `values.yaml`, with
  roles `["sessions"]`, `exposure = "private"`, its token in a `Secret`, its
  own PVC for the state directory and the work tree, and **reachable only from
  the door** (a `NetworkPolicy`).
- The door's `config.toml` is rendered from `values.yaml`: one `[host.<id>]`
  and one `[identity.<id>]` per person, each identity allowed its own host.

Each person gets their own process, so "one live session per `serve`" is per
person and roadmap #14 does not block this.

### Tools run in the container luu is in

The posture is `runtime = "host"` inside the image, and the image is the
sandbox: a non-root user, `readOnlyRootFilesystem` except the state and work
volumes, `capabilities: drop: [ALL]`, `seccompProfile: RuntimeDefault`, and a
`NetworkPolicy` for egress. **Landlock still runs inside** wherever the
node's kernel has it, which is the level-2-inside-level-3 shape the design
already describes. The image carries the toolchain the policy's `commands`
names, as `Containerfile` does today.

### The model is configured as it is locally

`[provider.*]` and `[engine.*]` unchanged. Keys are files, mounted from a
`Secret`. An owner edits them from Settings once the owner rule lands.

## In what order

1. **`[server]` with `exposure`, `bind`, `origin`.** `private` is today's
   token mode under a name. Plus the serve image and `deploy/compose.yaml`.
   Deployable behind Caddy with a token the day it lands.
2. **Passkeys, invitations, cookies, `auth.db`; `exposure = "public"`.** The
   token leaves the URL.
3. **`owner`**: Settings writes from a passkey login off loopback.
4. **`roles`, and the door**: identities to hosts, and the Helm chart.

Each step is a record of its own when it starts. This one argues the shape.

## What it costs

- **A WebAuthn implementation.** Writing one is how authentication bugs are
  made. `webauthn-rs` is the maintained Rust one, and it links OpenSSL through
  `webauthn-rs-core`, which this tree has avoided so far (rustls throughout).
  Whether a rustls-only path exists is the first thing step 2 checks.
- **Email delivery** is optional, and still a config table, a secret and a
  failure mode.
- **Two stores in the state directory**, and `auth.db` is the first that holds
  secrets. Its mode is checked, as `secret::read` checks a token file.
- **A public origin is configuration luu cannot verify.** Behind a proxy luu
  sees `http://luu:7878`. A wrong `origin` is a login that fails, never one
  that succeeds wrongly, because WebAuthn binds the assertion to the origin
  the browser saw.

## Rejected

- **A login proxy in front (oauth2-proxy, the ingress's auth) instead of
  passkeys in luu.** It is the usual Helm answer, and it was offered. Jesús
  chose email and passkeys. It also does not exist under Docker without a
  second service, and it leaves luu trusting a header.
- **Passwords.** Something to leak, reset and rate-limit, with passkeys
  available in every browser that can run this page.
- **A deployment mode** (`--docker`, `--helm`). It would give two answers to
  one question, and a laptop that wants a passkey would have to pretend to be
  a container.
- **Several identities in one `serve`.** That waits on concurrency (#14) and
  on per-identity permissions inside one session store. A pod per identity
  gets there without either.

## Still open

- **What a non-owner identity may do on a door** beyond reaching its hosts:
  nothing, to begin with.
- **Whether an identity's passkey login signs approvals**, which would make
  `[approvals] required` usable from the page without a separate key.
- **Provisioning on Helm** is a static list in `values.yaml`. Invitations
  that create a pod would need an operator, and that is not this.
- **`wss://` roots**: a laptop reaching the public server checks its
  certificate against Mozilla's roots today. A Let's Encrypt certificate passes;
  a private CA does not. See the appended section of
  [`a-project-is-a-host`](2026-10-02.a-project-is-a-host-a-folder-and-a-session.completed.md).

## Appended 2026-10-07: step 1 landed

- **`[server]`** with `exposure` (`loopback` | `private`), `bind`,
  `token-file` and `origin`, under `--exposure`, `--bind`,
  `--auth-token-file`, `--origin` and `LUU_EXPOSURE`, `LUU_BIND`,
  `LUU_AUTH_TOKEN_FILE`, `LUU_ORIGIN`. `public` is not a value yet: it arrives
  with passkeys, and accepting a word before its meaning exists is how a
  config file starts to lie.
- **An exposure is a promise.** `auth::resolve` refuses `loopback` with a
  public address or a token, and `private` with no token. The last refusal
  names `luu token`.
- **`luu token <PATH> [--if-missing]`**: 32 bytes from `/dev/urandom` as hex,
  in a file *created* `0600` (`create_new` with the mode, not a write and then
  a `chmod`). It never overwrites.
- **`origin`** is accepted as an `Origin` by the terminal's same-origin check.
  It is otherwise unused until passkeys, which bind an assertion to it.
- **`deploy/`**: `Containerfile` (the rust image, ripgrep, user `luu`
  10001, `/state` and `/work` as volumes), `entrypoint.sh`, `luu.toml` (the
  container's policy) and `compose.yaml` (luu read-only, `cap_drop: ALL`,
  `no-new-privileges`, with Caddy in front).

Run here with `LUU_DOMAIN=localhost`, through Caddy's own CA: the page at
200, the API at 401 without the token and 200 with it, the token `0600`
owned by `luu`, the process uid 10001, `enforce kernel` in the startup
lines, and a turn in the browser over `wss://` from prompt to reply.

**Found by running it:**

- **A granted path has to exist.** The policy grants `/state/cargo`
  (`CARGO_HOME`, so cargo can write somewhere on a read-only root), and on an
  empty volume it is not there, so the server refused to start and the
  container restarted in a loop. The entrypoint now makes it.
- **A fresh container has no model, and the page cannot add one.** Adding a
  provider is a Settings write, Settings writes are loopback-only, and this
  server is not on loopback. Until step 3 (`owner`), it is
  `docker compose exec luu` and an edit to `/state/config.toml`, or a file
  mounted there. That is the strongest argument for doing step 3 next, ahead
  of the door.
- **An empty `/work` is not a repository**, and `GET
  /api/workspace/git-status` answers it with a 500 and git's `fatal`. This is
  not new: a laptop's `serve` started outside a repository does the same. The
  panel should say "not a repository" rather than log an error. That is a
  small fix of its own.
