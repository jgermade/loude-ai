# A log for `serve`

## The problem

Jesús's `luu serve` froze twice on 2026-09-30, soon after opening Settings.
The second time it was measured: up 1:27, **0% CPU**, and every endpoint
(`/api/settings`, `/api/providers`, `/api/engines`) timing out at 5 s. That is
something waiting on something, not a loop. By the time a thread sample was
reached for, the process had been closed. It did not reproduce against the
same binary, the same `config.toml`, a copy of the same `sessions.db`, a
resumed session and a turn sent while the engine loaded.

And luu had nothing to read afterwards:

- about forty `eprintln!` lines on stderr, with no time and nothing per
  request;
- the session stream (`--record`, `sessions.db`), which records what the
  *model* did, not the server;
- the last 200 lines of each engine's output, in memory, gone with the
  process.

None of them can say *which request started and never finished*, which is the
one question a freeze asks.

## The proposal

`tracing`, which is already in the tree through axum and hyper, with
`tracing-subscriber` and `tracing-appender`, writing to
`<state dir>/logs/serve.YYYY-MM-DD.log`: rotated daily, seven days kept.

- **Every HTTP request, twice**: when it starts (an id, the method and the
  path, with the token left out) and when it ends (the status and the
  duration). A request that hangs is a start with no end.
- **A watchdog**: every five seconds, each request still in flight after five
  seconds is logged again at `warn`, with how long it has been waiting. If a
  lock is the problem, the watchdog runs on another thread and names the
  request stuck behind it. If the watchdog *itself* goes quiet, the runtime
  is blocked, which is a different answer and just as useful.
- **The events a freeze is likely to sit between**: the protocol socket
  opening and closing, a turn starting and ending, a session created or
  resumed, and each engine phase (`stopping`, `starting`, `ready`, `failed`)
  with its model.
- **The writer never blocks.** `tracing-appender`'s non-blocking writer hands
  lines to its own thread through a bounded channel, and drops lines rather
  than wait when the channel is full. A log added to find a freeze must not be
  able to cause one. That rules out the obvious shortcut of logging to stderr:
  a terminal that stops reading blocks every write to it, which is one of the
  hypotheses for this freeze.
- `LUU_LOG` takes a `tracing` filter (`LUU_LOG=debug`, or
  `LUU_LOG=luu=debug,tower=warn`). The default is `info` for luu's own
  crates and `warn` for everything else. `--no-log` turns it off, and the
  first lines of `serve` print where the file is.

The terminal keeps its `eprintln!` lines as they are. The log is a second
place, not a replacement, because a person watching `serve` start reads the
terminal and the lines there were written for them.

**Only `serve`.** `chat` and `stdio` are one process per run, and a hang there
is in front of whoever ran it. `serve` is the long-lived one, reached from a
browser, and where a hang is someone else's to diagnose afterwards.

**Rejected.**

- *`tower-http`'s `TraceLayer`*: the same two lines, plus a dependency's
  opinion of how to name the fields, and no in-flight table for the watchdog
  to read. An axum `from_fn` middleware is thirty lines and does both.
- *Logging the body or the query string*: the query can carry `?token=`, and
  the bodies carry prompts, which belong in the session stream, not in a file
  that is kept for a week.

## Built

As proposed. `crate::log` opens the file and holds the non-blocking writer's
guard for the life of `serve`. It has the request middleware, layered
outermost on the whole router, and the watchdog. `serve` prints the file's
place among its first lines, and `--no-log` turns it off. What it writes, at
the default `info`:

```
INFO luu::http: start id=4 method=GET path="/api/providers/blackhole/models"
INFO luu::http: end id=4 method=GET path="/api/providers/blackhole/models" status=200 ms=5004
INFO luu::ws: open socket=1 channel="protocol"
INFO luu::ws: client message kind="prompt"
INFO luu::session: session event="turn_started" turn="1"
INFO luu::session: session event="ended" turn="1" reason="stop"
INFO luu::engines: engine engine="llama_cpp" state="starting" model="ollama:qwen2.5-coder:14b" from="ollama:qwen2.5-coder:7b"
WARN luu::watchdog: still in flight id=7 method=GET path="/api/settings" secs=15
WARN luu::watchdog: the async runtime has not turned: every task is waiting on something that is not a timer secs=10
```

The page's own files are logged at `debug`, because a page load is thirty of
them and none of them is where a server hangs. The query string is never
logged: a request with `?token=secret` was checked to leave only its path in
the file. Neither are bodies, prompts, tokens or tool output. A turn sent as
"hola secreta" left the word nowhere in the file. The protocol events go
through `App::publish`, which every event already passes, as their type and a
fixed set of fields (turn, job, reason, tool, request, detail). `token` is
skipped.

**The watchdog runs on an OS thread**, not a task, for the reason the proposal
gave. Its two decisions are pure functions with tests: which requests are
overdue (`overdue`, which skips `/ws`, whose sockets stay open on purpose), and
whether the tick stopped (`Stall`, which reports every look while it is still
and once when it moves again).

**Found on the way: the intermittent `serve_ws` test.**
`a_guarded_port_hears_the_handshake_before_anything_else` and its sibling
failed about one run in three with "the auth token file … is empty", with or
without any change here. Two guarded servers in one test binary built the token
file's directory from the process id alone. They ran in parallel, and one read
the file while the other had just truncated it to write. Each call now gets its
own directory. Five runs in a row pass, where one in three used to fail.

## Still open

- The freeze itself. This record exists to catch it, and has not yet.
- `chat` and `stdio` have no log. See the proposal for why not now.

## Appended 2026-10-01: what it caught

It caught the freeze the same day, twice. Both times `GET /api/icon-theme`
was the only request in flight, for 98 s and then 147 s, and the tick stopped
for as long as it was. So it was a blocked runtime, not a lock. The handler
did its filesystem reads on a runtime worker, and it no longer does. Why the
disk was that slow is still not known: the log names the request but not the
syscall. See
[`2026-10-01.a-slow-disk-is-one-slow-request`](2026-10-01.a-slow-disk-is-one-slow-request.completed.md).
