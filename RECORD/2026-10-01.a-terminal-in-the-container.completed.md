# A terminal in the session's container

## The request

The third request in
[`the-foot-names-its-file`](2026-10-01.the-foot-names-its-file.completed.md):
an icon at the right of the content column's foot that opens a terminal
below the editor, in the container where the session's commands run.

Jesús answered the two questions that record left open:

- **The container gets a name** (`--name`, still with `--rm`), so the
  terminal can `exec` into it.
- **Where there is no container** (`host`, `direct`), the icon stays, off,
  and says why. No shell on the host from the browser.

## What changes in the decision it argues with

[`the-worker-and-the-seam`](2026-09-02.the-worker-and-the-seam.completed.md)
chose *the worker as PID 1* over *a keep-alive plus `exec` per tool call*.
Its first reason was that "there is no name to allocate, no `docker rm` to
forget, and no way to leave a container running after the session that
owned it died".

The worker stays PID 1, and tool calls still never `exec`. What this changes
is only the first clause: the container now has a name. The other two still
hold:

- **`--rm` is still the cleanup.** The name is not a handle anything has to
  release. When the worker's stdin closes, the container goes, name and all.
- **The terminal cannot outlive it.** An `exec` is a process *in* the
  container, so it dies with the container. The terminal's lifetime is
  bounded by the session's, the same way the worker's is.
- **A name per start, not per session.** A worker that is replaced after a
  stuck call starts again under a new name: `--rm` removes the old container
  asynchronously, and reusing its name would race that removal. The name is
  `luu-worker-<pid>-<n>`, unique on the machine for as long as the pid is.

The second reason, "no second lifetime to get wrong", is the one a terminal
does reopen, on purpose: an `exec` is a second process that can be alive
while the worker is being replaced. It touches nothing on the tool-call
path, though. The worker does not know the terminal exists, and a terminal
that dies tells the worker nothing.

## The proposal

- **`WorkerSpec`** names a contained run (`--name`) and builds the `exec`
  line: `<runtime> exec -it <name> sh -c 'exec bash || exec sh'` (colima
  with its `nerdctl --` prefix). It inherits the run's user, working
  directory and network, so the terminal is held to exactly what the
  worker is: the base mounted at its own path, the session's uid, and
  `--network none` when the session denies the network.
- **`Worker`** keeps the current container's name beside the pipe, not
  inside it, because the pipe's lock is held for the whole of a tool call,
  and a terminal should not wait behind a `cargo build`.
- **`luu serve`** gets `/ws/terminal`. It is under `/ws` so `?token=` reaches
  it the way it reaches the protocol socket, and it runs that `exec` line on
  a PTY (`libc::openpty`). Bytes cross as binary frames both ways, and a
  resize crosses as a text frame. `GET /api/terminal` says whether the live
  session has a container and, if not, why.
- **The page** draws it with `xterm.js`, an optional node dependency of
  `web/`, the way Monaco is one: served from `web/node_modules` by the
  binary and never embedded. Without it, the panel says how to install it.

## The authority it carries

A terminal is a person, outside the gate. The gate decides what the model
may do, and nothing a person types here goes through a plan. It is bounded
by the container and by nothing else. That is the reason the host gets no
terminal at all.

**It checks `Origin`.** A WebSocket is not covered by CORS, so any page in
any tab can open one to `127.0.0.1:7878`, and on loopback without a token
nothing else stands in the way. For the terminal that would be a shell for
every site the person visits. So `/ws/terminal` refuses an upgrade whose
`Origin` is not this server's own `Host`, and on an unguarded port it also
refuses a `Host` that is not loopback (DNS rebinding, the reason
`engines_allowed` checks `Host`).

`/ws` has the same exposure today and does not check `Origin`. Here the cost
would be a shell, and there it is an approval. Both are real, but fixing
`/ws` is not this change, and it is named here so it does not get lost.

## Rejected

- **A host shell when there is no container.** Declined at the gate: it is
  the whole account, from a browser.
- **A container just for the terminal**, from the image, beside a host
  session. That is a contained terminal next to an uncontained model, and
  the request was "where the commands run".
- **`docker exec -i` without a PTY**, which would need no `openpty`. No line
  editing, no job control, and every full-screen program breaks.
- **A drawn fallback without `xterm.js`.** A terminal is a VT100 emulator,
  and a `<pre>` with an input is not one.

## Still open

- `/ws` without an `Origin` check.
- Whether the panel's height should be dragged, like the columns' widths.

## Built, the same day

All of the proposal is built, and running it found one thing it had not
foreseen.

**Killing the `exec` client does not end the shell.** The first end-to-end
run closed the panel, the PTY's hangup reached `docker exec`, `docker exec`
exited, and `bash` was still PID 17 in the container. Docker does not
signal what an `exec` started when its client goes, and this container
lives as long as the session, so every closed terminal would have left a
shell behind it, along with anything running in the shell. So the line is
two lines now (`TerminalLine { open, end }`):

- `open` carries `-e LUU_TERMINAL=<pid>-<n>`, which the shell's children
  inherit;
- `end` is a second `exec` that reads `/proc/*/environ` (readable for the
  worker's own uid, which is every process a terminal starts), sends `HUP`
  to everything carrying the id, waits a second, and sends `KILL` to what is
  left. The script that does this does not carry the id, so it never
  signals itself.

After that, the same run left `docker-init` and `luu` in the container and
nothing else, a `sleep 900 &` included.

What the rest came to:

- **`WorkerSpec::argv_as`** puts `--name` before the image. `argv` is the
  same call with no name, so every existing test and `luu tools` are
  unchanged. `container_name()` is `luu-worker-<pid>-<n>`, one per start.
- **`Worker`** keeps the name in a `std::sync::Mutex` beside the pipe, and
  clears it wherever the pipe is dropped: on `replace`, and on a broken pipe
  in `call`. A terminal asked for while the worker is dead says so instead
  of `exec`ing into a container that is going away.
- **`crate::terminal::Pty`** is `libc::openpty`, `setsid` and `TIOCSCTTY`
  in `pre_exec`, and two plain threads on the master. It is unix-only, and
  a build without it answers the socket with a sentence. Three tests run it
  without a container: a command on it is on a TTY at the size it was
  opened at, a resize reaches it, and a hangup ends one that would not end
  on its own.
- **`/ws/terminal`** is refused with `403` for a foreign or missing
  `Origin`, and on an unguarded port for a non-loopback `Host`. It is
  refused with `409` and the reason when the session has no container.
  `serve_ws.rs` covers all three without a runtime.
- **The page**: `lib/terminal.js` owns the shell, and
  `views/editor/terminal.html` is the box it is drawn in. Hiding the panel
  moves xterm's element out of the page and the shell keeps running; *end*
  ends it; *open again* appears when it ended on its own. Its colours are
  the page's tokens, read when it is drawn. `/api/terminal` is asked once
  the socket has found a server, and never in a replay: the static twin
  answers it with a 404, and the site suite caught that.
- **`terminal.spec.js`** is the whole thing in a real container, against
  `luu.container.toml`: the worker's uid, the base at its own path,
  `TERM=xterm-256color`, the same shell after hide and show, and nothing of
  it left in the container after *end*. It **skips itself** where there is
  no daemon or no `luu-worker:dev` image, which is the CI `web` job today.

One cosmetic thing it shows: the prompt reads `I have no name!@…`, because
the worker runs as the host's uid and the image has no passwd entry for it.
That is bash saying the truth, and fixing it means writing to the image's
`/etc/passwd` at start, which nothing else needs.

## Still open, after building it

- `/ws` without an `Origin` check, as above.
- The panel's height is fixed at 16rem.
- `scripts/container-check.sh` does not exercise the terminal. CI builds the
  image there and not in the `web` job, so the spec that does is skipped in
  CI. Joining the two is the way to get it run on every push.

## Superseded the same day: the host gets a terminal

Jesús changed the second answer once the panel came out disabled on his

included, and its panel moves the session between postures. The host shell
is offered by default only to a browser on this machine. How, and what that
argues with, is in

## 2026-10-02: luu's prompt, the author's colours, and the host's `~`

Jesús asked for the container's prompt to look like his zsh one
(`rc.zsh` in github.com/jgermade/sh), then for its colours to match his
terminal's, and then whether the path it showed was right.

- **The prompt is luu's, not the image's.** `exec_argv` used to start a
  plain `bash`. Now it starts `bash --rcfile /dev/fd/3` with the rc passed
  in on a here-document, because the container is not ours to write to. The
  rc runs after `/etc/bash.bashrc` and `~/.bashrc`, so those still apply,
  and it replaces only `PS1`:

  ```text
   luu@docker ~/dev/joshua/luu  light-page-monokai-and-scrollable ⚡  ▸
  ```

  - `luu@` plus the runtime, passed in as `LUU_RUNTIME`.
  - The directory in yellow.
  - The branch on blue, with `⚡` when `git status --porcelain` lists
    anything. `git` is asked with `safe.directory=*`, because the base is
    the host's and the shell runs as another uid. A git that refused would
    only leave the branch out.

  This also ends the `I have no name!@…` above, because the prompt no longer
  names the user. `sh`, where there is no bash, keeps its own prompt.
- **The panel has a palette.** `theme()` gave xterm only a ground, an ink,
  a cursor and a selection, so the sixteen ANSI colours were xterm's own
  Tango. Its yellow, `#c4a000`, is a step duller than the one the prompt
  was written for. The sixteen colours are now tokens on the panel
  (`--ansi-yellow`, `--ansi-bright-yellow`, …), filled from his
  `joshua.itermcolors`, and `theme()` reads them. They belong to the panel,
  so a host shell gets them too.
- **The path stays, and `~` moves to match it.** The prompt showed
  `/Users/JG31772/dev/joshua/luu`. The first proposal was a fixed
  `/home/luu/<project>`: mount the base there, or link it there and open
  the shell on the link. Moving the mount argues with the decision in
  [`the-worker-and-the-seam`](2026-09-02.the-worker-and-the-seam.completed.md):
  a fixed mount point would make a contained run and a host run differ in
  their bytes. The link would have kept the mount, but at a cost: an `exec`
  as root to make `/home/luu`, and two names for one directory. He agreed
  to keep the path, and asked for the other half of the same idea instead:
  **the container's `HOME` is the host's.** `WorkerSpec::home` defaults to
  the `HOME` of whoever started the session and is passed at `run` as
  `-e HOME=…`, so the worker's commands and the terminal both have it.
  Bash shortens `\w` by comparing the text of the path with `$HOME`, so the
  base reads `~/dev/joshua/luu` with nothing made or linked. The directory
  exists in the container, because the runtime makes the mount's parents.
  It is root's and not writable, as the `/` it replaces was not.

### Checked

- `cargo test --workspace` passes, including a new test that `HOME` is said
  at `run` and not again at `exec`, that the terminal names its runtime, and
  that a spec with no home says nothing.
- `terminal.spec.js` passes against `luu-worker:dev`. It now asserts
  `H=$HOME` is this machine's, and that the prompt reads
  `luu@docker ~/…` and then the branch.
- A screenshot of the panel shows the path in `#ffe816` and the branch on
  `#3465a4`.

### Still open

- `HOME` now reaches the model's commands as well. A tool result that
  prints `$HOME`, or a `~` that a shell expands, will now read the host's
  path inside the container, where before it read `/`. That is the point,
  but no probe in `scripts/tasks/` has been re-run since.
- The prompt and the palette are the author's, written in. Nothing in
  `config.toml` changes them yet.
