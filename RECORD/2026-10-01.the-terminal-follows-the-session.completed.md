# The terminal follows the session, and the session can move

## The request

Jesús, after the terminal in
[`a-terminal-in-the-container`](2026-10-01.a-terminal-in-the-container.completed.md)
came out disabled on his machine:

> entiendo que la ejecución de los comandos debe ejecutarse siempre en un
> entorno, ya sea el host local o en un contenedor, por lo que el terminal
> debería estar siempre disponible
>
> la idea es que desde las opciones del terminal se pueda cambiar de entorno
> de ejecución

Two questions came back with answers:

- **What moves when the environment changes:** the live session. The
  model's commands move with the terminal, not just the terminal.
- **The host shell:** loopback only by default, and configurable in
  `config.toml`.

## What this argues with

**First, "a host session gets no terminal"**, from the record above. That
was the answer to a question asked that same day, and the person who gave
it has changed it. The argument behind it still holds, so it is kept where
it can be: a host shell is the whole account, so by default it is offered
only to a browser on this machine. That is the rule `engines_allowed`
already applies to starting a process here, for the same reason. `direct`
counts as the host: its worker is a child on this machine, with no
container.

**Second, "a posture may not move"**, from `luu-design.md` and
[`what-an-approval-was-granted-under`](2026-09-17.what-an-approval-was-granted-under.completed.md).
That record found three ways a posture that moved under a session went
wrong:

1. the fold dropped it;
2. a resume that moved only the posture wrote no line, so the recording
   described a posture the turns did not run under;
3. a signature does not bind it.

Each one comes from *something approved under one posture being carried
into another*, or from *a move the stream does not record*. Neither is
inherent to moving. So the proposal moves the posture **between jobs and
in writing**:

- **Refused while anything is approved or asked.** That covers a running
  turn, a proposal waiting at the gate, and an approved job still open. The
  refusal names which one, and closing the job is the way through. Between
  jobs a session runs under its posture's floor (read-only), so nothing
  granted is carried across.
- **Written down as a header line.** It goes into the stream, the
  `--record` file and the fold, carrying the new posture. The fold's "last
  header wins" already means *from here on, this ran somewhere else*, and
  that is exactly the fact. It is checkpointed at once, the same as a
  resume's line, so a session moved and then left alone still says so.
- **Built before anything is swapped**, the same as `create_session`. A
  runtime that is not installed, or an image that is not built, refuses the
  move and leaves the session where it was. The old agency is ended
  explicitly, and its container goes with it, along with any terminal in
  that container.

Signatures (3) are untouched: an approval is made at the gate, after the
move, against what the gate shows.

## The proposal

- **`[terminal] host` in `config.toml`:** `"loopback"` (the default) offers
  the host shell only when `serve` is bound on loopback *and* the request's
  `Host` is loopback. `"always"` offers it to anyone `/ws/terminal` admits,
  which off loopback means the token. `"never"` offers it to nobody. A
  container shell is unaffected.
- **The host shell** is `$SHELL -l` (or `/bin/sh`) on the PTY, in the
  sandbox's base, with `TERM=xterm-256color`. It needs no `end` line: the
  PTY's hangup reaches it directly, because there is no runtime in between
  to swallow it.
- **`PUT /api/session/posture`** takes `{ "posture": "<name>" | null }`,
  where `null` is the server's own policy file. The postures offered are
  the ones `/api/postures` already lists, so what a page may pick is still
  bounded by what somebody typed in `config.toml`.
- **The terminal panel** gets an environment picker in its bar: the server's
  own, plus every `[posture.<name>]`. Choosing one moves the session, ends
  the shell that was in the old environment, and opens one in the new.
  `/api/terminal` says where a shell would open (`host` or the container)
  and why not, when it would not.

## Rejected

- **Moving the terminal and not the session.** Declined at the question. A
  terminal somewhere the model's commands are not is a terminal that
  answers a different question from the one being debugged.
- **Moving the posture with a job open, and re-gating it.** The job's plan
  was resolved against the old sandbox, and re-resolving it silently is the
  2026-09-21 widening one field along. Closing it first is one click and
  says what happened.

## Still open

- A pre-signed approval made before a move and presented after it. Job ids
  are positional, so it is admissible. It needs a signer who signs ahead of
  the gate, which nothing here does today.

## Built, the same day

All of it, as proposed, and running it in the page found one bug of the
page's own.

- **`[terminal] host`** is `provider::Terminal`, defaulted where the file
  says nothing and carried through every writer that rebuilds the file. A
  misspelled key or value is an error, like every other table.
- **The host shell** is `$SHELL -l` in the sandbox's base, on the same PTY.
  `serve_ws.rs` opens one through `/ws/terminal` on a loopback server, types
  `echo LUU_$((40+2))`, and reads `LUU_42` back. The arithmetic is so the
  line matched is the shell's answer and not the echo of what was typed.
- **`PUT /api/session/posture`** holds the session lock for the whole move,
  so no turn can start between the check and the swap. The move refuses a
  proposal at the gate (`409`, "gate") and an approved job (`409`, naming
  it). A name the file does not have gets `400` and moves nothing. A move to
  where the session already is answers `moved: false` and writes nothing.
  The test also reads the fold (`/api/sessions/live`), which is what a store
  and an export read, and finds the new posture there.
- **The panel's picker** is the `Dropup` component, listing the server's
  own policy file and every `[posture.<name>]`. `terminal.spec.js` now
  moves a real session from its container to the host and back: the shell
  answers `IN=host` and then `IN=container`, using `/.dockerenv`, which
  tells the two apart on a Linux host too. The second container is a new
  one, because the first went with the move.

**The bug:** the first run moved nothing, while the picker's face said
"host". `Dropup` writes its `:model` back before it emits `change`, so the
guard `name === here` compared the new name with itself. The guard now
compares against what the server last said, and a refused move asks the
server again, so the picker goes back to where the session still is rather
than showing where it was asked to go.

## Still open, after building it

- A pre-signed approval across a move, as above.
- `/ws` without an `Origin` check, carried from
  [`a-terminal-in-the-container`](2026-10-01.a-terminal-in-the-container.completed.md).
- A login shell is as slow to start as the person's own rc files make it.
  On this machine that is long enough that a screenshot taken a second after
  opening shows the typed line before the prompt. Nothing is lost, because
  the PTY buffers it, but it reads as a hang.

## The panel goes under the file's foot

Jesús: *"el footer del terminal debe quedar debajo del terminal, y el
terminal debajo del footer del fichero"*. The column now reads: tabs, the
file, the file's foot, the terminal, and the terminal's foot. The bar that
sat on top of the panel is that last foot, `--chrome-h` tall like every
other foot, so it lines up with the inspector's and the chat's at the
bottom of the page. The file's foot stays against the file it describes.
The environment picker is a dropup, which is what a foot at the bottom of
the window wants.

## Its controls are icons

*end* and *hide* were words, and every other control in a foot on this page
is an icon. *end* is a bin (`#i-trash`), because it ends the shell for good.
*hide* is a chevron down (`#i-chevron-down`), because it puts the panel away
and keeps the shell. They are different shapes because they make different
promises. *open again* is `#i-refresh`, the shape the page already uses for
reading something again. What each one does is in its `title`, and the
specs find them by it.

## The picker is named by where it runs

Jesús: *"y si reemplazamos 'on this machine' por un selector de runtime"*.
Two readings were put to him, and he chose the first:

- **The posture, shown by its runtime.** One picker, as before. Its face is
  `host` or `docker · luu-worker:dev`, and each option names the posture
  and the file under it. A runtime this machine does not have is offered,
  off, saying so.
- **A runtime of its own**, beside the posture. Rejected, because the two
  are one file on purpose: `luu.container.toml` grants `[[worker.paths]]`
  that exist only inside the image, so `luu.toml` on Docker, or the
  container posture on the host, is a sandbox naming paths that are not
  there. *"The posture decides the sandbox and the seam together, because
  one file decides both"* stays true.

He also asked what *server default* is and what it implies. It is the
policy file `luu serve` was started with: `--sandbox <file>`, or `luu.toml`
in the directory it was started in, or, where neither exists, the built-in
policy that grants nothing beyond the implicit roots. What it implies:

- **It has no name.** The recording writes `name: null`, and a resume
  compares it with other postures on the three facts and never on the name.
- **It is read again for every session**, so an edited `luu.toml` is what
  the next session (or the next move onto it) gets.
- **The flags `serve` was started with apply to it and to every named
  posture alike.** `--worker docker` moves them all into Docker, and
  `--allow-read` widens them all.

What was built:

- **`SandboxArgs::describe_posture`** reads a policy file's `[worker]`
  block and the flags over it, and asks `which` for the runtime's program.
  **It never builds the posture**, because building is what starts a
  container, and a picker that started one per option to say what each one
  is would cost a VM boot every time it opened. An image that is not built
  is the one thing it cannot tell without asking the runtime, and the move
  says so when it is refused. `serve` gets it as a closure,
  `describe_for`, beside `agency_for` and for its reason.
- **`/api/postures`** gains `own` (the server default) and `places` (each
  posture), each `{ policy, runtime, image, missing }`.
- **The words beside the picker are gone while a shell is open.** The
  picker says where it runs. They come back for what the picker cannot say:
  *connecting*, *ended*, *moving the session…*.

Tested: a unit test describes a host file and an Apple-runtime file without
starting either, and finds the second *not installed* wherever `container`
is absent. `serve_ws.rs` reads `places` off `/api/postures`, and
`terminal.spec.js` picks the host by its runtime's name and its line,
`host · luu.toml`.

## Every container runtime, as a variant of a contained posture

Jesús: *"ahora mismo sale host y docker — y las otras opciones? (nerdctl
colima container)"*. They did not appear because the picker lists postures,
and his file names two: the server's own (`luu.toml`, host) and
`container` (docker). He chose, out of three, to have every contained
posture offered on every container runtime.

**The argument.** "One file decides the sandbox and the seam" holds
between the host and a container: `[[worker.paths]]` exist only inside the
image. Between container runtimes it does not hold. They share one image,
one set of in-image paths, and one argv but for its first word, which is
the reason `Runtime` is a name rather than an integration. So a variant
swaps one container runtime for another and changes nothing else.

**And the rule it keeps.** `NewSession::posture` says the browser never
types *a runtime and an image*, for the reason it never types a URL. A
variant is one of five words compiled into luu (`Runtime::CONTAINED`), the
image is still the file's, and `posture_for` refuses the two moves that
would break the argument above: a variant that is not a container runtime,
and a variant of a posture that runs on the host. Both are `400`s with the
reason.

What was built:

- `resolve_posture` and `describe_posture` take the variant as the
  `--worker` flag, for one session. The factories `serve` holds take it
  too.
- `/api/postures` lists `own` and each posture as **a list**: the posture's
  own runtime first, and, where that is a container, the other four after
  it. A host posture is a list of one.
- `create_session`, `resume_session` and `PUT /api/session/posture` take
  `runtime` beside `posture`. A session moved to podman can then be resumed
  on podman. Without that, the resume would be refused for running
  somewhere else, with no way to name where.
- The picker's value is `posture|runtime`. The option shown as chosen is
  read off the runtime the live session reports, so it is the one the
  session is actually on.

On this machine the picker now shows host, docker, and podman, nerdctl,
colima and Apple's `container` off, each saying that its program is not
installed. `serve_ws.rs` checks the order of the list and the three
refusals, and `terminal.spec.js` checks that an uninstalled runtime is
offered off.

An image is per runtime: Podman and containerd do not see Docker's images.
A variant whose runtime is installed but has no `luu-worker:dev` is refused
when it is chosen, with the runtime's own words, because finding that out
beforehand means asking the runtime, and the picker never starts anything.
