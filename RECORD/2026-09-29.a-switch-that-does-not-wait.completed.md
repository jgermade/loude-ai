# A switch that does not wait, and tool calls the chat can read

Jesús reported two things from using the page. The page froze when the model
was changed. And while a model called a tool, the chat showed it typing the
```` ```tool ```` block character by character, then pasted the answer straight
onto the closing fence. They are separate changes, but both are about what the
page shows while something is still happening, so they share this record.

## The switch

**What happened.** Choosing a model in the chat's picker sends
`POST /api/sessions` (or `/resume`). `destination_for` called
`Supervisor::ensure` and awaited it before answering. For a llama.cpp engine on
another model, `ensure` stops the server, downloads luu's copy if needed,
starts it with `-m` and polls the port every 300 ms until it answers or
`ready-timeout` passes. Meanwhile the picker kept its menu open over a
full-window backdrop, every model disabled, and "Switching…" in its foot. With
a 14B that lasted tens of seconds, and nothing on the page moved.

The server was not blocked. No lock is held across the wait, and other requests
were answered. What looked frozen was the page, and it looked frozen because
the request did not return.

**What changed.**

- `destination_for` no longer waits. It wraps the backend in
  `engines::Started`, which runs `ensure` before every call it sends. Once the
  engine answers, `ensure` costs one health probe.
- `create_session` and `resume_session` call `Supervisor::warm` once the session
  points at the new destination and the other engines are released. `warm` runs
  `ensure` in a task and returns.
- `serve`'s own warm-up at startup wraps its backend the same way. The first
  turn used to meet a closed port if it was sent before the model loaded. Now it
  waits on the load.
- `ensure` runs one at a time per engine, behind a per-name lock. Without it,
  the warm-up and the first turn raced: both saw the old model, both stopped the
  engine, and the loser could stop the model the winner had just loaded.
- `Supervisor::readiness` keeps where each engine's last `ensure` ended up
  (`loading`, `ready` or `failed`, with the model, the seconds in that state and
  the error). `GET /api/engine` returns it for the live session's engine, or
  `null`. The page polls it once a second while `loading`, starting from
  `checkModel`, which every switch path already calls. The picker's button shows
  `loading 12s` or `engine failed`, with the reason as a tooltip.

**What it costs.** A turn sent during the load looks like a turn that is slow
to start: the assistant message is empty until the model loads. The button
beside the composer says why. An engine that fails now fails the *turn*
(`failed`, with the engine's own tail) instead of the switch, so the session
has moved to a destination that cannot answer yet. Before, a failure left the
session where it was. The new behaviour is right for a load that is merely
slow, which is the common case. For a binary that is missing, the old
behaviour was better, because the switch was refused before anything moved.

**Rejected.**

- *Keep waiting, but close the menu and show a spinner.* The request would
  still hold the page's other awaits (the picker's `switching`, the
  `refreshSettings` behind it), and a second switch during the load would queue
  behind the first on the server.
- *A protocol message for engine state.* A new variant of a tagged enum is a
  protocol version bump. The read side already has a place for this, and a poll
  that only runs while something is loading costs nothing the rest of the time.
- *Disabling the composer while loading.* `checkModel`'s own argument applies:
  a provider that is starting up is an ordinary state. The turn waits on the
  server anyway.

**Tested.** `engines::tests::a_warm_engine_is_waited_on_by_the_backend_and_says_why_it_failed`:
`warm` reads `loading` from the moment it is called, a call through `Started`
gets the engine's failure as its first chunk, and `readiness` then reads
`failed` with the same reason. No test starts a real engine. Nothing in CI has
llama-server.

## Tool calls in the chat

**What happened.** The model writes a call as text. The server streams every
token, the call included, because the protocol carries what the model produced.
`parse_call` reads the call only after the step ends, and then emits
`tool_call` and `tool_result`. Those went to `state.tools`, which only the
debug inspector reads. The chat drew `message.text` as it was, so a turn that
used a tool read like this:

````
voy a leerlo
```tool
{"name":"read_file","arguments":{"path":"AGENTS.md"}}
```Es el fichero de instrucciones compartido.
````

**What changed.** The reading moved to the page, at render time.
`ui/segments.js` splits an assistant reply into text and tool parts, using
`parse_call`'s two forms: a ```` ```tool ```` fence, or a bare `{"name": …}`.
The bare form is only recognised at the start of a line, because this is a
guess about what to *hide*, and prose that quotes an object mid-sentence should
stay prose. Each block that parses is paired, in order of `step`, with the
turn's calls. A call the text does not show in a recognised form is still drawn
after the text, because a call that ran is never hidden. While the reply is
live:

- a block that has opened and not closed is a placeholder ("writing the
  call…");
- a closed block waiting for its `tool_call` reads "waiting…";
- a tail that could be the start of a block (a line that begins with one to
  three backticks, `` ```to ``, or `{"na`) is held back, so the placeholder is
  not preceded by a flash of backticks.

`ui/tool-call.html` draws each call as one line: the name, what the call is
about (`argv` joined, `path`, or the first string argument), how it went
(`done`, `denied`, `failed`, `exit N`, `running…`, `not run`) and how long it
took. The verdict, the arguments, stderr, the output and, for a block that never
ran, what the model wrote are behind a click.

**Why at render time and not on the wire.** Both halves the page needs were
already there, live and after a reload. The turn's text is the concatenated
tokens in both cases: `SessionView` folds `Token` by `push_str`, exactly as
`appendToken` does. The calls are in `state.tools` for the running turn and in
`state.history[turn].tools` for every other, which `keepTurn` and a reload both
fill. So no protocol version, record format or stored shape moved, and a
recording made before today draws the same cards.

**Rejected.**

- *Split the text server-side into per-step messages.* That is a protocol
  change (a new variant, v9), and it would make the store say something the
  model did not produce. The inspector's raw prompt and text would then have to
  be reassembled to show what was sent.
- *Stop forwarding tokens once a fence opens.* It hides the call from every
  client, the recorder included, and the fence is only the model's intent: a
  block that never parses still has to be readable somewhere.

**What it does not do.** The text a model writes *after* a closing fence in the
same step (`CallVerdict::ContinuedPastFence`, the precision run's invented
results) cannot be told apart from the next step's answer. Both are drawn as
the text after the card, as they were before, minus the fence. And a bare
object in the middle of a line is still drawn as prose, with the card
appended after the text.

**Tested.** `tests/smoke/gate.spec.js` already drives a `read_file` through the
gate against the mock. It now also asserts that the card reads
`read_file · README.md · done` and that no assistant article contains
```` ```tool ````. 23 of 23 pass. The segmenter was also driven by hand in node
over the streaming cases (a partial fence, a partial bare object, a closed call
waiting for its result, two calls in one turn, a normal `rust` fence, a
mid-line object).

**Found on the way.** The smoke suite picks `target/release/luu` over
`target/debug/luu` when both exist, and release embeds the UI at build time.
A release binary older than the change under test ran the old page, and the new
assertions failed. `LUU_BIN=target/debug/luu` is what tested this change. Also,
`serve_ws::a_guarded_port_hears_the_handshake_before_anything_else` fails about
one run in three with "the auth token file … is empty", with or without this
change.

## Still open

- Whether a switch should refuse up front for an engine whose binary cannot be
  resolved. That check is cheap and synchronous, and it would bring back the
  old behaviour for the one case where it was better.
- `run_command`'s card could show stdout inline when it is short. `write_file`
  and `edit_file` could show a diff instead of the arguments' JSON. Both need
  only `call.arguments`, which the card already has.
- The smoke suite's binary choice should be the newer of the two, or say which
  one it took.
