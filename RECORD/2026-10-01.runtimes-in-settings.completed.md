# Runtimes in Settings

## The request

Jesús, once the terminal's picker offered all five container runtimes and
greyed out the four this machine lacks: *"añade en settings lo necesario
para configurar/habilitar los runtime"*.

A container runtime is usable by a session when four things are true, and
today the page can see none of them and change none of them:

1. **it is installed**, meaning its program is on `PATH`;
2. **it answers**, meaning Docker's daemon is up, Podman's machine is
   running, Colima is started;
3. **it has the image**: each runtime keeps its own store, so
   `luu-worker:dev` built in Docker is not in Podman;
4. **a posture uses it**, either by naming it or as a variant of one that
   names another container runtime.

## The proposal

A **Runtimes** section in Settings, between Engines and Models, with three
parts.

**The runtimes.** One row per container runtime, with the answer to each
of (1)–(3):

- the program's path, or *not installed* and how to install it, as text
  to copy. luu installs nothing that needs the person's package manager or
  `sudo`.
- whether it answers: `info` (`container system status` for Apple's), run
  with a five-second clock, and the first line of what it said when it did
  not answer.
- every image a contained posture names, present or not
  (`image inspect`), and **build** where it is missing. That runs
  `<runtime> build -t <image> -f Containerfile .` in the base, as a
  background job whose last lines the section shows while it runs.

The probes run when the section is opened and when *check again* is
pressed, never on a timer: each one starts a process, and on Docker
Desktop each one wakes a VM. While a build runs, only the build's state is
polled.

**The postures.** `[posture.<name>]` from `config.toml`: add and remove. A
new posture names a policy file **out of a list**, not one the browser
types. The list is the `*.toml` files at the top of the base that carry a
`[sandbox]` or a `[worker]` table, so `Cargo.toml` is not on it even though
it would parse as an empty policy. Each one is shown with where it would
run (`describe_posture`), so what is being added is visible before it is.

**The host shell.** `[terminal] host`: loopback, always, or never.

Every write is held to `engines_allowed`: loopback by the bound address
*and* by `Host`. The reason is that one engine has: a posture is what a
session may do, and a page on a rebinding domain must not be able to add
one.

## What this argues with

`/api/postures` says: *"Read-only, and deliberately so: a posture is a
policy file, and a page that could write one would be a page that could
widen its own sandbox."*

The page still never writes a policy file. It writes a *name* for one that
already exists on this machine, which is what `config.toml`'s providers and
engines tables already let it do for destinations and processes, from
loopback only. The widening that sentence guards against is the page
choosing a broader file. That is real, and it is bounded the same way the
providers editor is: a person at this machine's browser, choosing among
files somebody wrote into the checkout. The one honest gap is a job with
`writes` that writes a permissive `*.toml` into the base and waits for
somebody to add it. The list shows each file's runtime, network and
writable roots before it is added, which is a person reading what they
approve, the same as the gate.

**Postures stop being read once.** `serve` read them when it started ("a
posture added to `config.toml` is offered by the next run"). A posture
added from Settings and absent from the picker until a restart would read
as a broken save. So `App::postures` becomes a lock, and a write replaces
it. A session already on a posture keeps its agency, since what it runs
under was built when it moved. A posture removed while the live session
uses it is refused: the session would be running under a name the file no
longer has.

## Rejected

- **Installing runtimes.** Docker Desktop, Podman and Colima are packages
  with their own installers and, on Linux, root. The section says the
  command and does not run it.
- **Editing a policy file from the page.** That would be the widening the
  read-only sentence exists to stop.
- **Probing on a timer**, for the reason above.

## Still open

- Apple's `container image inspect` and `container build` are the shapes
  its CLI documents. Neither has been run here, because it is not
  installed.

## Built, the same day

All three parts, as proposed.

- **`Runtime`** gained the lines this needs, as argv like everything else
  in that layer: `invocation` (colima's `nerdctl --` included),
  `probe_argv` (`info`, or `system status` for Apple's), `image_argv`,
  `build_argv` and `install_hint`.
- **`crate::runtimes`** runs them. `probe_all` asks the five at once, each
  under a five-second clock, and skips the image questions for a runtime
  that is not installed or did not answer. `Builds` runs one build per
  runtime and image, keeps its last 40 lines, and refuses a second build of
  the same pair while one runs. `policy_files` is the list, and the test
  that pins it has a `Cargo.toml`, a broken TOML file and two policy files,
  and finds the two.
- **Routes:** `GET /api/runtimes` (the probes, the builds, the postures and
  policy files each with where it would run, the host rule);
  `GET /api/runtimes/builds` (what the page polls while a build runs, and it
  starts nothing); `POST /api/runtimes/{runtime}/build`; `PUT /api/postures`;
  `PUT /api/terminal`. The writes go through `engines_allowed`. A build
  takes only an image that some policy file here names, for the reason a
  posture never takes a path the page typed.
- **`App::postures`** is a lock now, and the posture move, the picker and
  `/api/postures` all read it through `App::postures()`.

**Run here.** `/api/runtimes` answered in 0.8 s on this machine: docker
installed, answering, with `luu-worker:dev` built, and the other four not
installed, each with how to install it. A build started through the route
rebuilt `luu-worker:dev` from this checkout. The page's tail followed it
through `cargo build` inside the image and it ended `exit status: 0`. The
image's creation time moved to the minute it finished.

**Tested.** `settings.spec.js`, against its own `config.toml`, adds a
posture by name and file and finds it in the file and in `/api/postures`
without a restart. It then removes it, gets `422` for a path out of the
list and `400` for an image no file names, and closes the host shell. That
writes `host = "never"`, and `/api/terminal` then refuses with that reason.
Opening it again writes no `[terminal]` table at all.

One trap, found by that test: the add form's `<option>`s read `adding`
while the save set it to `null`. jq79 said exactly which expression, and
`?.` was the fix.

Running the whole suite afterwards found one thing that was not this
change. The two specs that open a host shell had been running the login
shell of whoever runs them (`$SHELL -l`). On this machine that is a `zsh`
whose `.zshrc` runs `ssh-add`, which had started asking for a passphrase,
so both tests waited at a prompt for an answer that never came. They now
start `serve` with `SHELL=/bin/sh`. The product keeps `$SHELL -l`, because
a person's own `PATH` is what a terminal on their machine should have, but
a test must not depend on a person's rc files.

## Later the same day: installing and starting, where no root is needed

Jesús: *"se podrían instalar los runtime desde la modal de settings?"*.
Above, "Installing runtimes" was rejected because each runtime is "a
package with its own installer and, on Linux, root". That is true of three
of them and false of two, and the two are worth having:

| runtime | install from the page | start from the page |
| --- | --- | --- |
| podman | `brew install podman`, on macOS with `brew` on `PATH` | `podman machine init` if there is none, then `podman machine start` |
| colima | `brew install colima`, the same | `colima start --runtime containerd` |
| docker | no: Docker Desktop is an app with a privileged helper | `open -a Docker`, on macOS |
| container | no: Apple's is a signed `.pkg` that needs an administrator | `container system start` |
| nerdctl | no: there is no macOS build, and on Linux it is root's | no: containerd is a system service |

Homebrew is the line drawn. On this machine it lives in the person's home
directory (`~/homebrew`), and anywhere it is installed it refuses to run as
root, so `brew install` is a process with the person's own authority. That
is the same authority `luu serve` already has when it downloads an engine's
release into the state directory. A package manager that needs `sudo` is a
different authority, and the page still only says the command.

The rest stays as it was. Every step is a fixed line `crate::runtimes` writes,
and the page names only the runtime. The routes are `engines_allowed` and take
a JSON body, like `start_engine`, so a cross-site form cannot send them. The
builds become **tasks** (`build`, `install`, `start`), all shown and polled the
same way.

Built. `crate::runtimes::install_steps` and `start_steps` hold the lines in
the table above. `Tasks` runs install, start and build alike: steps in
order, stopping at the first that fails, one per kind, runtime and image.
The routes are `POST /api/runtimes/{runtime}/install` and `…/start`, and
`/api/runtimes/tasks` is what is polled. The rows show *install* with the
exact command beside it, or the reason in a few words (*not from here: its
package needs an administrator*). A runtime installed and not answering
shows *start it*.

Tested without installing anything on the machine that runs the suite.
`settings.spec.js` puts a stand-in `brew` first on the server's `PATH`
whose `install podman` leaves a `podman` that answers `info` and has no
images. The page installs it, and the row goes to *answering* with the
image *not built* and a build button. A unit test pins the three runtimes
that are never installed from here and that nerdctl is never started.
Another runs a three-step task whose second step fails, and checks that
the third never ran.

**A bug the full suite found, and the alone run did not.** The page
re-asked the runtimes when a task ended from a `$:` line that watched for a
running task. It woke when the task outlived the first answer and not when
it finished first, so on a fast stand-in the row stayed *not installed*.
The same lines had also assigned the route's answer, a task list, to the
whole view. Starting a task now follows it explicitly, and the list goes
into `view.tasks`.

Also, from the same message: the inspector's `ready` is green (`--ok`, a
new token, which is the history bucket's green so the page still has one
green), and so are *answering* and *built*, which were already asking for
`--ok` and falling back to the accent. Runtimes moved between Models and
Sessions, since a posture is chosen per session.
