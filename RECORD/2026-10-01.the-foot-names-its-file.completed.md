# The content column's foot names its file, and shows its diff

Three requests from Jesús about the content column's foot:

1. keep the file's name where it is, and in place of the language as a word,
   put the file's icon before it, the same one the tree draws;
2. right after the name, while the file has changes, a button with an icon
   that shows `git diff` in a modal;
3. at the far right, in place of the *diff it* link, an icon that opens a
   terminal below the editor, in the container where the commands run.

The first two are built. The third is not, and its own section says why.

## The icon

The foot draws what the tree draws for the same name: `iconFor(basename,
false)` from `lib/workspace.js`, so a theme's art where `[ui] icon-theme`
names one and the page's `#i-file` where it does not. A debug tab has a
title and no file, so it gets `#i-sliders`, the shape its tab already has.

The language did not disappear. It is the `title` of the icon and of the
path, because it is still the one fact the highlighter decided, and a word
in a 40px bar was spending width the path needs more. The highlighting smoke
test asserts it there now: `title="rust"`, `title="make"`, and an empty one
for `.gitignore`, which has no grammar.

## The diff, as a glance

A button (`#i-diff`, a plus over a minus) sits right after the path. It is
there only when `workspace.status` has the open file: the status the tree
already reads, so it appears and goes as the disk changes, with no request
of its own. It is not on a diff tab, which already is one.

It opens `views/editor/diff-modal.html`, which asks `/api/workspace/git-diff`,
the endpoint the diff tab asks. **The file stays on screen.** That is the
whole difference from the *diff it* link it replaces, which opened a tab and
covered what you were reading. The diff tab still exists, opened from the
Git panel, for reading a diff at the column's width.

- **It opens on the side that has something.** Git's code is two columns,
  index then working tree. `M ` is staged with nothing left in the tree, and
  opening that on *working tree* would show an empty answer that reads as "no
  changes". So that case opens on *staged*, and every other on *working
  tree*.
- **Both sides are one click away**, for the reason the diff tab's foot has
  both: a panel that shows one side silently lies when the other exists.
- **It follows the disk.** It asks again when `workspace.status` is
  replaced, which happens after every batch the server reports. It is
  memoized on the path, the side and the status object, because jq79 wakes
  a line on a write to any field of `workspace`, and the tree had already
  paid for not doing that (see
  [`the-page-in-web`](2026-10-01.the-page-in-web.completed.md)).

The hunks moved out of `editor.html` into `views/editor/hunks.html`, which
both the tab and the modal draw, so the two cannot drift.

`workspace.spec.js` has the case end to end, in its scratch repository: a
committed file shows no button, an edit from outside brings it, the modal
shows the line removed and added, staging it while the modal is open empties
the *working tree* side, *staged* shows it, and closing leaves the file in
the column.

## A trap in jq79, found by moving the hunks

`<Hunks>` in `editor.html` came out as a plain `<hunks>` element holding
the rest of the template. The same tag worked in the modal.

jq79 cuts a file at `<script…</script>` and `<style…</style>` before it
rewrites PascalCase tags into components, and the regex does not know about
comments. A comment above, written months ago, mentioned the scoped style
block by its tag. From there to the real `</style>` the file was "style",
and nothing in it was rewritten. It had been harmless because nothing in
that stretch was a component.

The comment says it in words now, and a note above `<Hunks>` says why. The
fix that belongs upstream is jq79 skipping comments when it cuts. No other
file in `web/` has the same shape today.

## The terminal: not built, because it reopens a decision

[`the-worker-and-the-seam`](2026-09-02.the-worker-and-the-seam.completed.md)
decided that **the container's only process is `luu worker`**, not a
keep-alive that is later exec'd into. So there is no name to allocate,
nothing to `docker rm`, and no container can outlive its session. A terminal
"in the container" is an `exec` into it, which needs exactly the name that
decision did without. `--name`, or `--cidfile`, plus `--rm`, would keep the
cleanup. But that is a change to an argued decision, and AGENTS.md says such
a change argues with the decision rather than routing around it.

Two more facts it has to answer before it is code:

- **A terminal is a person, outside the gate.** The gate decides what the
  *model* may do. A shell in the browser is whatever the container (or the
  host) allows the uid that runs it. Inside the container that is the
  bind-mounted base and, under most postures, `--network none`. On a host
  session it would be the whole account, one request away from anyone who
  holds the token.
- **Most sessions have no container.** `[worker] runtime` defaults to `host`,
  and this machine's `config.toml` names no posture, so every session here
  runs its tools in-process. A contained session also starts its worker on
  its first tool call, not when it opens, so a terminal could find nothing
  to attach to.

What it costs once decided: a PTY on the server (`docker exec -it` wants a
TTY, and `libc::openpty` is already in reach), a socket route that carries
bytes both ways under the same token as `/ws`, and a terminal on the page
(`xterm.js`, as an optional node dependency the way Monaco is one).
