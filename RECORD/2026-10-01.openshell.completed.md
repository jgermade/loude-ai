# OpenShell, read against the worker seam

## The question

Jesús, after the terminal's picker came to name runtimes: *"tb estaba
pensando en https://github.com/NVIDIA/OpenShell"*. He asked for a study and
no code.

**What this is made of.** OpenShell's README, its architecture and policy
pages, its CLI reference, and two of its issues, all read on 2026-10-01.
Nothing was installed or run. Where a claim below is about behaviour, it is
the documentation's claim and not something observed here. Sources are at
the bottom.

## What it is

NVIDIA's "safe, private runtime for fleets of autonomous AI agents":
Apache-2.0, version 0.1.x, Linux first, with macOS on Apple silicon and
WSL 2 listed. It has three parts:

- **a gateway**, the control plane: who you are, which sandboxes exist,
  which policy and credentials each one gets;
- **a supervisor**, the trusted side of each sandbox: it checks every
  network request against the policy, resolves DNS, opens the approved
  connections, and adds credentials to them;
- **the sandbox**, the untrusted side: it owns the agent's processes,
  applies Landlock to the filesystem and seccomp user notification to
  network calls, and identifies which program made each request from
  `/proc`.

The workload has no network of its own. Its only way out is the channel to
the supervisor. On Docker or Podman that is two containers, a supervisor's
and a workload's with networking disabled; on Kubernetes, two pods; on a
microVM, a guest with no network device.

A policy is YAML (`version: 1`) with five sections. `filesystem_policy`,
`landlock` and `process` are fixed when the sandbox is created.
`network_policies` and `network_middlewares` can change while it runs. An
"advisor" and a "prover" review a policy change before it applies.

The surface is a CLI plus SDKs in Python, TypeScript, Go and Rust:

```sh
openshell sandbox create --name demo --from <image|Dockerfile> --policy p.yaml --upload ./src:/workspace
openshell sandbox exec -n demo -- ls -la /workspace
echo hello | openshell sandbox exec -n demo -- cat        # stdin is piped
openshell sandbox exec -n demo --tty -- /bin/bash
openshell sandbox upload demo ./more /workspace
```

## How it would sit behind the seam

It fits the seam's shape better than it might seem. `[worker] runtime` is a
command line, never an API ([`the-worker-and-the-seam`](2026-09-02.the-worker-and-the-seam.completed.md)),
and OpenShell has a CLI that pipes stdin:

| luu needs | OpenShell has |
| --- | --- |
| a long-lived worker on stdio | `sandbox create --from luu-worker:dev`, then `sandbox exec -n … -- luu worker` |
| the terminal's shell | `sandbox exec -n … --tty -- bash` |
| ending it with the session | `sandbox delete` |
| a manifest of commands | the image, unchanged |

So a `runtime = "openshell"` is a variant of `WorkerSpec::argv` plus a
create and a delete around it. That is more than the other five need: their
container *is* the worker, and here the sandbox outlives the process that
`exec`s into it, which is the "keep-alive plus `exec`" shape the seam
record turned down. Its argument against that shape was two lifetimes that
can disagree, and that argument comes back with it.

## Where it does not fit

**Files cross by copy, not by mount.** `--upload` and `sandbox upload` stage
files into the sandbox. luu mounts the base *at its own absolute path*,
because a contained run and a host run of the same script have to be
diffable byte for byte, and because a job's `writes` are meant to land in
the person's checkout. That checkout is what the tree, the git panel and
the diff modal show. Under a copy:

- a write stays in the sandbox until something copies it back, and nothing
  in the protocol says when;
- the tree follows a disk the model is not writing to;
- every path in a verdict or a tool result is a sandbox path, so the "one
  flag apart" comparison is lost.

This is the decisive gap. It is a property of OpenShell's sandbox, and no
flag on luu's side changes it.

**Two policies for one question.** luu already answers *what may this
touch* twice, with a plan narrowing a policy file, and both are enforced by
the same `Sandbox` (Landlock, the seccomp filter, rlimits). OpenShell's
YAML enforces the same three things on the far side. Running both means
deciding which one is the outer bound, and making a denial name the right
one. Today it always does: "the plan refused" and "the policy refused" are
different sentences. With a third policy layer underneath, a third
sentence is needed, and so is a way to keep the YAML and the TOML from
drifting apart.

**A control plane.** A gateway is "bootstrapped automatically" when none is
running. luu's worker is a child of the session with no daemon, no port and
no token ("the pipe's authority is the parent's"). A gateway is a second
process with its own lifetime and its own identity, and that is exactly
what the seam was built not to need.

## What it does that luu does not

**Egress per destination, with credentials added at the boundary.** luu's
network is whole: a session may reach it or not, a job may narrow that, and
`## egress:` names hosts. Nothing in luu holds a credential *for* the
model. OpenShell's supervisor does two things:

- the workload never sees a key, and the supervisor adds it only to a
  request bound for an endpoint the policy allows;
- the policy can change while the sandbox runs, through a review step.

The first is the interesting one for luu. A job that may call one API, with
a key the model never sees, is a grant the gate could express (`## egress:`
already names the host) and the sandbox could not enforce. That is a
proxy, and it can be built inside luu's own seam: a supervisor-shaped
process on the host side of the pipe, the worker's network denied except to
it. Adopting OpenShell is not needed for that.

## Verdict

Not as a runtime, for as long as files cross by copy: it would break the
diffability the container layer was built around, and make the tree show a
disk the model does not write to. **Worth borrowing:** the egress model,
that is, a mediated proxy as the only way out, an allowlist per
destination, and credentials injected rather than handed over. That would
be its own record when a job first needs a key.

## Still open

- Whether OpenShell can mount instead of upload. The CLI reference
  documents only `--upload`. If a mount appears, the decisive gap closes
  and the two-lifetimes argument is what is left.
- Its macOS story. The README lists Apple silicon, and the architecture
  page names only Linux mechanisms. On a Mac the Landlock half would be
  inside a VM, which is luu's situation with Docker Desktop too.
- Nothing here was run. The first thing to do, if this comes back, is
  `sandbox exec … -- luu worker` against `luu-worker:dev`, and checking
  that the handshake survives the pipe.

## A correction, the same day

"luu's network is whole: a session may reach it or not, a job may narrow
that, and `## egress:` names hosts". That sentence, and "a grant the gate
could express … and the sandbox could not enforce", were wrong about the
second half. `agent_core::sandbox::proxy` is a host-side CONNECT proxy that
reads the destination's hostname without terminating TLS and filters it
against the job's `egress` list. So *only this host* is enforced today, and
was before this study was written. It was missed because the study read
OpenShell's documentation and not luu's tree.

What OpenShell has and luu does not is therefore narrower than the study
said: **credentials injected at the boundary**, so that the model never
holds a key. That needs the proxy to see the request, which means
terminating TLS, and that is the part luu's proxy deliberately does not do.
The verdict stands, and the thing worth borrowing is smaller and more
precise.
